## 001 · Mermaid 时序图解析报错：参与者命名撞了语法关键字（2026-10-12）

- **现象**：L0 总体设计的「Tick 主循环」时序图渲染失败，报错 `Expecting '+', '-', 'ACTOR', got 'loop'`，整图不显示（owner 在 GitHub 预览时发现）。
- **定位**：参与者命名用了 `Loop`，与 Mermaid 时序图的语法关键字 `loop`（循环块）撞名且大小写不敏感，解析器把它当关键字而非参与者；另外消息文本里的 ASCII 括号/方括号/花括号 `()[]{}` 属于语法字符，会干扰文本解析。
- **决策与理由**：① 参与者改名 `DRV`，彻底避开关键字族（loop / alt / opt / par / rect / break / note…）；② 消息文本统一用全角（）「」替代 ASCII `()[]{}`——全角标点是 Unicode 字符，不在语法字符集内。命名避开 DSL 关键字 + 文本避开语法字符，一次修复两个隐患。
- **教训**：给图表工具（本质是 DSL，Domain-Specific Language，领域特定语言）写脚本时，**标识符先查该语言的关键字表**——"能起的名字"和"该起的名字"是两回事。这条直觉可迁移：SQL 列名、配置键名、任何 DSL 标识符都要先想关键字冲突。

## 002 · 确定性测试在空实现下"平凡通过"（2026-10-13）

- **现象**：切片 01 红相位（实现故意留空）跑测试，8 处断言失败——但 `hash_state(wa) == hash_state(wb)`（同 seed 两遍一致）这条**居然通过了**。
- **定位**：两个空实现的世界状态完全一致（都是空的），哈希当然相等。"同输入 → 同输出"在实现什么都不做时天然为真——**确定性断言本身无法证明系统做了任何事**。
- **决策与理由**：测试分组设计成行为断言与确定性断言**成对出现**：`tick==10 且 pos==2.5`（行为）与 `hash(同 seed 两遍)==`（确定性）缺一不可；红相位把两者同时暴露（行为失败、确定性平凡通过），绿相位两者同时转绿才可信。
- **教训**：这是测试设计的一般规律——**"不变式断言"必须搭配"进展断言"**（数学上：不变量在零状态下总成立）。任何"每次结果都一样"类的测试，要么配一个"结果确实变了/动了"的测试，要么它什么都不守护。迁移场景：幂等性测试、缓存命中测试、序列化往返测试。

## 003 · C++20 兼容性疑虑：用一次降级实验代替争论（2026-10-14）

- **现象**：owner 注意到"很多项目还在用 C++11、C++17/20 很少见"，担心 C++20 兼容性差（第二次提出此关切；第一次按策略答复，本次补上实验证据）。
- **定位**：① 事实核查——重建至今的代码（core / world_state / truth_world）**零 C++20 专属特性**，全部是 C++11 级设施（struct / enum class / uint64 算术 / 模板）；"C++20"是 CMake 的一个设置，不是代码的依赖。② "很多项目用 C++11"是存活偏差——C++11 已 15 岁，那个年代起步的代码库因 ABI/消费者兼容约束留在原地；本仓库是单机应用、无外部链接方，不共享该约束。
- **决策与理由**：做实验而不是辩论——把 CMake 的 `CXX_STANDARD` 20 改到 17 重建：**一次通过，ctest 2/2 全绿**；恢复 20 再验一遍同样绿。结论：保留 C++20 设置（工具链已实证 + 代码未依赖新特性 + 降级路径一行可切），boring-core 纪律不变。
- **教训**：兼容性问题要用**降级实验**回答（改一行、编一次、跑测试），不要用观点争论；"设置里选的版本"与"代码实际依赖的特性"是两件事——定期用实验确认这个差距，就是把兼容风险钉死在纸面上。

## 004 · 自注册宏撞上 token-paste：带限定名的类型不能过宏（2026-10-14，切片 03）

- **现象**：`OW_REGISTER_PERCEPTION("blob_detect", ow::BlobDetect)` 编译炸出一串错（`make_ow` 不是命名空间 / 类型重定义 / 未定义基类——症状完全不像根因）。
- **定位**：宏对参数做 `##` 粘贴（`make_##TYPE` → `make_ow`）：宏参数被当作**裸标识符**拼接，`::` 处断开；而我把类藏进了匿名名字空间，裸名又不出作用域。两种写法单用都行，叠一起就死。
- **决策与理由**：约定——注册宏的 TYPE 参数必须是不含限定的裸名，且宏调用点放在同一 namespace 内。症状与根因相隔两层，这是宏错误的通病。
- **教训**：自注册宏一族的三条坑齐了：① MSVC 静态库丢注册对象（用 OBJECT 库）② 跨 TU 静态注册顺序不定（枚举按名排序，不靠注册序）③ token-paste 不吃限定名（裸标识符约定）。可迁移到一切注册/反射/TEST 宏场景。

## 005 · 聚合 ECE 被高产低信息的生产者淹没（2026-10-14，切片 06 对齐运行）

- **现象**：Gate-1 对齐运行里，诚实检测器与"夸大检测器"的聚合 ECE 几乎相同（0.4977 vs 0.4963）——指标看不出谁是故意注入的错误置信度。
- **定位**：ECE 把**所有生产者**的条目混入一个总池。当次运行 9746 条里，世界模型贡献了 9600 条（2 模型 × 8 实体 × 600 tick），它们置信度固定 0.5 而准确率≈1.0 → 每条约 0.5 的 |acc−conf| 项，把检测器那 ~300 条的真实差异彻底淹没。**指标本身没错，是聚合丢掉了结构。**
- **决策与理由**：pre-rebuild 的回归报告是**按 producer 分表的 ECE**（blob_cc 0.0115 vs miscalibrated 0.9732）——旧设计的"分表"正是防这个坑的。v1 聚合版记录为已知缺口：**per-producer ECE 列入阶段 B**（Metrics 深模块公开接口已就位，纯增量）。
- **教训**：**聚合指标先问"各分量的量级与信息量"**——平均数会把信号最弱、批量最大的那个分量变成主角。任何"全体平均"型指标（平均延迟、平均误差、总分）都要同时保留"按来源分解"的视角。


## 006 · 指标分离幅度依赖场景，跨场景比阈值先比场景（2026-10-16，切片 B4 重测）

- **现象**：阶段 B 恢复 per-producer ECE 后重测判据 (c)：诚实（0.199）vs 夸大（0.010）分离量 0.189，**低于 pre-rebuild 的 0.30 阈值**——分离机制明明已生效。
- **定位**：幅度差在场景而非机制。① 诚实检测器 conf≈0.73 在观测良好的早段欠自信（acc=1 → ece≈0.27），晚段实体飘出观察窗口拉低 acc，被抹平；② 旧阈值 0.30 是 pre-rebuild 场景（弹墙、blob_cc 特定校准）的产物，与新场景（无墙常速）不同源——拿旧尺子量新场景本身就不严格。
- **决策与理由**：如实裁定 (c) 维持 PARTIAL；把"关闭判据 (c)"挂到 F2（有界场景）之后的**场景固化重测**，而不是当场调阈值迁就数字（那就破坏了 Round 1 #2 的判据可比性）。
- **教训**：**跨场景比较指标前，先比场景参数，再比阈值**。任何从旧基线搬来的判据（延迟预算、分离线）都要先问"这把尺子是在什么场景下校准的"。

## 007 · 指标分离幅度是场景故障的属性，不是指标机制的属性（2026-10-16，F2 墙场景重测）

- **现象**：F2 有界场景落地后重测判据 (c)：分离量 0.184（blob_detect 0.194 vs overconfident 0.010），仍低于 pre-rebuild 的 0.30 线——与 006 同因，墙未能改变它。
- **定位**：夸大检测器的检测算法与诚实版**完全相同**（同一连通块逻辑），仅置信度公式不同——合成场景里它的准确率≈0.98，于是 0.99 的自报反而接近校准（ece≈0.01）。pre-rebuild 的 0.30 分离出自"夸大者真的错"的故障注入场景；本场景没有该故障，尺子量不到它。分离幅度是**场景故障结构**的属性，不是分解机制的缺陷（分解与可编程判定在 B4 已证）。
- **决策与理由**：判据 (c) 在环部分维持 PARTIAL，并把关闭明确留给阶段 C 的真实模型场景（真实世界模型的错误结构 ≠ 合成确定性场景）。不调阈值迁就数字。
- **教训**：当“指标判别力不足”时，先分清是**机制**坏了还是**场景**没有注入目标故障——006/007 两轮把方向指向后者，避免了对指标的无效改造。合成场景校准指标时，故障注入本身就是测试用例设计的一部分。

## 008 · "零幻觉"被写成契约级验收：模型能力边界不是接口不变式（2026-10-19，切片 C3）

- **现象**：C3 的 L2 把"全背景帧 → 空 Proposal 列表（无幻觉项）"列为验收测试 3。实测空白帧返回 **1 个框**，置信度 0.330，且是 `w=h=1` 的整帧退化框（模型自报类 `tvmonitor`）；8 实体合成场景同样只有 1 个退化框（0.518，自报 `laptop`）。AC 直接红。
- **定位**：该 AC 假设了"COCO 检测器对无物体输入零误报"。这是模型在**分布内**（自然图像）的经验性质，被顺手写成了**契约属性**。纯色 + 几个 2×2 色块的合成帧在训练分布之外，检测器对它没有任何"输出空"的义务；而"过阈值"≠"有语义的检出"——0.330 那个框就是模型在没东西可报时的默认姿态（整幅 + 屏幕类）。
- **决策与理由**：**改判据，不改场景迁就模型**（L2 §3 早已定了后者这条）。断言换成 `size ≤ 5` + 两次调用逐字段相等：上界保留回归捕获力（后处理若错到 sigmoid 套两次 → ~300 框必红），确定性这条真正的契约属性保留。"链路正确"的正证据改由**真实照片**那一栏承担（5 框，类别/位置/尺度与图像内容逐一对上）。
- **教训**：写 AC 时先问一句——**这条性质是接口保证的，还是模型恰好具备的？** 前者可以断言具体值，后者只能断言边界（有界、单调、可复现），**不能断言"零"**。同族坑：把第三方库/外部服务的经验行为写成本地契约测试。C4 的 L2 起草时直接套用这条检查。
- **复现与加强（2026-10-19，切片 C4）**：同一陷阱在**同一个切片内**复发了两次。① L2 §5 我为"纯平帧 → 空列表"写了行为行；② 写测试时又差点按直觉写下 `CHECK(a.empty())`。实测：**RGB 全 0x80 的纯灰帧产生 32 条结构化深度提案**（格均值区间 [0.795, 3.260]，spread 2.465）——为"退化帧"写的空输出分支一次都没触发。ViT 会从位置编码里造出结构，模型不会把"没有信息"翻译成"没有输出"。断言改为"有界（≤32）+ 确定性"后绿。**结论：008 不是一次性教训，而是每次写模型侧断言时的默认检查项。**

## 009 · 隔离层把异常压成计数器，故障原因在工件里蒸发（2026-10-19，切片 C3）

- **现象**：`--ep cuda` 跑完，工件里只有 `adapter_faults: 1`。真正原因（`onnxruntime_providers_shared.dll` 没拷到 exe 目录）只出现在 ORT 自己打到 stderr 的日志里，JSON 一个字都没有。
- **定位**：隔离层是 `catch (...) { ++faults; }`。设计意图是对的——单个适配器故障不得 halt tick 循环（这是适配器不变式的一部分）；但它把异常文本一起丢了。**"能继续跑"和"能解释为什么没跑成"是两件事**，v1 只做了前者。
- **决策与理由**：`RunReport::first_fault`（格式 `生产者名: what()`），两处 catch 都填、只留第一条；同时把 `quote()` 扩到转义 `\n\r\t` 与控制字符——自由文本进 JSON 的前置条件。B1 工件 schema **只增字段**，既有字段与顺序不动。修掉 CMake 的 DLL 拷贝后复跑：工件里现在完整写着 `CUDA EP unavailable (... Failed to load shared library); needs CUDA 12.8+/cuDNN 9 (see docs/17-research/...)`——交接材料第一次自带诊断。
- **教训**：**任何"吞掉异常换取存活"的设计，必须同时留一条最小诊断通道**（第一条原因 + 来源标识），否则可观测性归零，故障计数变成一个只能看不能查的数字。同族：`ignore_errors` 循环、静默 fallback 分支、降级开关。

## 010 · 可选依赖让"恰好 N 项"型断言在另一构建配置下失效（2026-10-19，切片 C3）

- **现象**：ON 构建（`OW_WITH_ONNXRUNTIME=ON`）第一次跑**全量**套件，`ow_slice03` 红：`names.size() == 2` 失败（实际 3）。默认 OFF 构建一路绿，所以这条断裂潜伏了三个切片。
- **定位**：两层。① 注册表测试断言的是"全局恰好 2 个适配器"，而阶段 C 把适配器变成**可选编译单元**——注册项数量从此是构建配置的属性，不是行为的属性。② 流程漏洞：C1 引入 ON 构建后，ON 侧只跑过新切片的单测（slice13），跨配置矩阵从未跑全，所以没有测试替它发现。
- **决策与理由**：断言按配置**精确化**（`kExpected = ON ? 3 : 2`，并逐项核对名字），**不**放宽成 `>= 2`——精确集合既守住"没有意外条目混进来"，又承认注册表随配置增长。同时把"ON 构建跑全量 ctest"写进收口动作（C3 报告的 15/15 是第一次）。
- **教训**：① 引入可选依赖后，凡断言**全局基数**（条目数、枚举长度、注册表大小）的测试必须显式绑定配置，否则它测的是构建开关而不是行为。② **新构建配置一旦存在，它的全量套件就是必须跑的**——只跑新切片的测试等于没有那个配置。C4 会再加一个注册项（→ 4），这条测试就是它的哨兵。

## 011 · 动态轴导出的 ONNX：静态元数据只够分类，尺寸必须运行期取（2026-10-19，切片 C4）

- **现象**：深度适配器第一版跑起来即抛 `unexpected output extent`，测试进程**无声退出**（exit `0xC0000409`，零输出）。同一份代码里 RT-DETR 适配器一直正常。
- **定位**：我用 `GetOutputTypeInfo()`（**会话期**静态元数据）去取输出的 H/W 并据此分类布局。DA-V2 的导出图声明的是**动态轴**——输入探测为 `[-1,3,-1,-1]`、输出为秩 3 的动态形状，于是 H/W 读回来全是 `-1`，`mh <= 0` 直接命中抛错分支。RT-DETR 侥幸没事，是因为它的输出恰好是静态的 `[1,300,4]` / `[1,300,80]`——**同一段代码在两个模型上一个能跑一个不能，差别不在我的逻辑而在图是否导出为动态**。更糟的是抛出点在 `observe()` 之外被测试直接调用，异常无人接 → 进程 fastfail，连"哪一步错了"都没留下。
- **决策与理由**：两层各修一处。① **适配器**：静态元数据只用于"秩/通道"分类，真实尺寸一律从运行期张量 `GetTensorTypeAndShapeInfo().GetShape()` 取（与 `rtdetr.cpp` 读 boxes/logits 的做法对齐——它本来就这么写，我没照做），并把实际 dims 与元素数写进异常消息；② **测试**：新增 `try_observe()` 包装，把"抛异常"变成**带名字的失败**而不是静默崩溃。修好后同一次运行直接打印出 `predicted_depth dims [1,518,518]` 与照片上的 `[1,392,518]`，keep-aspect + multiple-of-14 的行为当场得到确认。
- **教训**：① 对**导出图**编程时，"形状"有两个不同的东西——图声明的形状与本次运行得到的形状；凡是动态轴可能存在的位置，都必须按运行期值处理，静态值只配做分类。② 新模型第一次跑通之前，**任何直接调用它的测试都要有异常出口**，否则失败形态是"进程消失"，而调试一个没有输出的崩溃基本等于重做一遍。③ 同族代码不等于同族正确：另一个适配器能跑，不能作为"我这段读法安全"的证据。

## 012 · 判据的关闭条件可能是场景前提，不是实现进度（2026-10-19，切片 C5 / 阶段 C 收口）

- **现象**：判据 (c)（"ECE 能判别正常模型 vs 注入错误置信度"）从阶段 A 起挂着 PARTIAL，两轮诊断（006/007）都指向"合成场景没注入目标故障，等真实模型进场就能关闭"。真实模型果然进了环（C3/C4），重测却给出：诚实侧 0.199（合成对）/ **0.242（真模型 vs 注入者）**，分离量仍 **< 0.30**；而**被注入错误的那个始终是 ECE 最低、看起来最校准的一个（0.010）**。更决定性的：同一个 `rtdetr_v2_s`，换面板换 seed，ECE 在 **0.24–0.49** 之间漂移。
- **定位**：前提错了，不是进度慢了。判据要的是"一个接近校准的正常模型"这一席位，而**这个席位需要模型的定义域与真值域相交**。本世界的真值是 y≡0 平面上 8 个彩色方块，COCO 检测器在其中没有可对应的对象——它的 correct 只能来自"框心碰巧落在某实体 0.1 半径内"。**一个随场景漂移 0.25 的量，不可能同时是"这个模型校准得好不好"的量。**所以无论实现多完善，该判据在阶段 C 的世界里都不可关闭。
- **决策与理由**：如实裁定 PARTIAL，并把**关闭条件重新定位**到 Phase 3（真实视频 + 真标注，那时检测框第一次有可比真值）。三条"不做"：不把 0.30 调到 0.25 让它过线（006/007 已立此纪律）；不把"数值上有分离"当成判据达标；**不把该结论写进测试**——`slice16` 只冻结面板参数与 ECE 字面量，故意不断言"分离量 < 0.30"，否则一个未达标的判据会在每次 CI 里显示为绿灯。
- **教训**：当一条判据被归因为"等某个前置到位就能关闭"时，**先验证那个前置是否提供了判据所指的语义，而不只是提供了新的实现对象**——真实模型进环是进度，真实模型**有可比真值**才是判据前提；两者容易被当成一件事。配套纪律：判据的失败形态如果只能靠人读报告发现，那就绝不要让它能以"测试通过"的形态出现。

## 013 · 生成脚本的转义层会静默吃掉反斜杠序列（2026-10-26，切片 D3）

- **现象**：Git Bash 里用 `printf` 生成"进入 MSVC 环境再构建"的 bat，两次翻车，症状完全相同：一片 `fatal error C1083: 无法打开包括文件 "cstdint"`（还有 `"map"`、`"cstddef"`）——像是构建目录或编译器坏了。第一次 `printf` 直接报 `missing unicode digit for \U`（路径里的 `C:\Users`），生成的 bat 残缺，`vcvarsall` 没执行；第二次把路径改写成不含 `\U` 的形式，`printf` 不报错了，但 bat 里变成 `<VT>cvarsall.bat`——**`\v` 是垂直制表符**，于是 `call` 找不到文件（`The system cannot find the path specified.`），`INCLUDE` 仍为空，同一个 C1083 复发。
- **定位**：`printf` 的**格式串同时是数据**。反斜杠后跟 `n t v U x a b f r 0` 等都会走 C 转义表，其余大多原样透传——所以故障只在少数几个字符上出现，且**取决于路径里恰好有什么**：上次踩 `\U`（`Users`），这次踩 `\v`（`vcvarsall`）。上次记下的规避办法是"避开 `%` 和 `\U`"，那是清单式排除，注定漏。
- **决策与理由**：规则从"避开哪几个序列"升级为"**格式串只放结构，数据一律走参数**"：`printf '@echo off\r\ncall "%s" x64\r\n' 'D:\...\vcvarsall.bat'`——参数不做转义展开。同类判断适用于任何"脚本生成脚本/配置"的路径：JSON、YAML、PowerShell 字面量各有自己的转义层。
- **教训**：**同一条坑第二次出现，说明上一次的规避方式治标不治本**——要把它改写成结构约束，而不是往排除清单上再加一个字符。另外，症状相同的两次故障不要当成同一个原因结案：第一次修完"能跑"不等于根因清楚，`if defined INCLUDE` 那一行探针输出才是把"环境没进对"与"代码有问题"分开的证据。

## 014 · 清单相对路径的解析基准是清单所在目录，子目录前缀不能省（2026-10-26，切片 D3）

- **现象**：真实面板建好后 `--frames data/panel/frames.txt` 报 `frame source: cannot open frame 'data\panel\frame_0000.rgb'`。因为本仓库已有 `/tmp` 与 `$TEMP` 打架的前科，第一眼像 Windows/Git Bash 的路径分隔符或 cwd 问题；实际帧文件在 `data\panel\frames\` 下。
- **定位**：`FileFrameSource`（D2）按设计把清单每一行解析为**相对清单文件自身所在目录**——这是刻意行为，好处是整份面板可以整体搬运。生成端 `coco_to_panel.mjs` 把帧写进 `frames/` 子目录，却只登记裸文件名：**两侧对"相对谁"的理解不一致**。读侧没有错，错在写侧。
- **决策与理由**：修生成端（清单里写 `frames/frame_0000.rgb`），不动解析语义——为迁就一个工具 bug 去放宽路径规则，会把"清单可整体搬运"这个已测试的性质悄悄降级。同时立一条流程：**清单类产物写完必须立刻用消费者读一遍**，而不是检查"文件存在"。本次就是一次 `--ticks 5` 的运行（几秒）当场抓出来的，比任何单测都便宜。
- **教训**：路径报错在本仓库有一个固定反射——"先怀疑平台/编码"，而这个反射每次都要花时间去证明它**不是**平台问题。真正的判别办法是只看一件事：**写侧与读侧各自认定的基准目录是什么**。凡是"一个文件里列路径、另一个文件去解析"的设计，就要把这条边界写进文档，并在第一次产出后端到端消费一遍。

## 015 · 分母会收缩、空集也算相等：两个指标会把退化的系统排得更好（2026-10-27，研究笔记 E1）

- **现象**：交互闭环研究笔记的实验 E1（观察时滞 → 信念误差，200 帧真实面板，零核心改动）里，**系统明显退化，而两个现有指标都变好了**。纯感知系列中，时滞让"信念覆盖率"从 30.5% 掉到 21.0%（匹配到的实体少 31%）、检测器 ECE 恶化 47.8%（0.198829 → 0.293768），可 `divergence` 只涨 18%（0.053283 → 0.062999）；带神谕世界模型的系列里 `divergence` **不涨反跌**（0.010747 → 0.009333）。更反直觉的是 `identity_stability`：**时滞越大分数越高**（0.130653 → 0.276382）。
- **定位**：两个指标各自有一个未声明的语义边界。① `DivergenceMetric` 只对 **Matched** 的主张求平均（`src/metrics/metrics.cpp`），不匹配的主张不计入误差——于是**分母随退化收缩**，只留下"恰好落在真值附近"的那批主张，平均误差自然变小。② `IdentityStabilityMetric` 比较相邻两 tick 的"匹配实体 id 多重集"是否相等；而标注面板每 tick 是**新场景**、`next_id_` 从不复用 ⇒ **非空集合绝不可能相等** ⇒ 相等的唯一可能是**两边都空**。算术验证：把 `identity_stability` 当作 P(相邻两 tick 都零匹配) 反解 p_empty，六个 lag 推出的"每非空 tick 匹配数"落在 2.00–2.41 的窄带内 ⇒ 假设成立。**一个什么都不相信的系统会拿到 identity_stability = 1.0。**
- **决策与理由**：**本轮不改代码**（无 owner 批准的 L2，且这两项属 D4/Phase 4 的口径范畴）。改为：① 在研究笔记里把两条缺陷连同证据写死，并给出三条具体修改建议——加**覆盖率**指标（applied / 全部信念）、把 divergence **按 producer 分解**（仿 `ece:<producer>`）、空集不等于稳定（要么排除空-空配对，要么只在有真实 track id 的数据上用该指标）；② **D4 重测判据 (c) 前必须逐条核对**：判据 (c) 量的是"真模型 vs 注入者"的 ECE 分离量，而 D3 面板上 ECE 已经被证明会随"输入是否对得上真值"漂 0.20→0.29——**分离量必须连同覆盖率一起报**，否则可能复现同一个陷阱；③ 闭环指标**成组发布**（误差 + 覆盖 + 计数）写进 Phase 4 的报告口径。
- **教训**：① **均值类指标必须连同分母一起报**——"平均误差变小"和"系统变好"是两件事，只报前者的指标在退化场景下会系统性地说谎。② **空集参与比较时，相等的语义要显式裁定**：两个都没有信念，和两个信念稳定，是完全相反的两件事，但 `==` 分不出。③ 指标本身也会"过期"：D3 已经如实标注本面板的 identity_stability "无语义"，但**"无语义"不等于"无害"**——它仍然被打印、仍然可以被引用、而且方向是反的。④ 一条可推广的检查法：**把系统故意做坏，看指标是否还朝着"变差"的方向动**；如果不动或反向，这个指标就不能单独用于判据。

## 016 · 省略 `--models` 不等于关闭世界模型（2026-10-27，研究笔记 E1）

- **现象**：做"纯感知"对照时，第一版实验把 `--models` 整个省略，本以为没有世界模型在环，结果工件里出现了 `predict:zero_delta` 与 `predict:linear_extrapolation` 两个阶段键，账本条目从 2 229 变成 3 448——**实验条件与预期不符，且工件本身带着足以发现它的证据**。
- **定位**：CLI 的默认配置里 `cfg.world_models = {"zero_delta", "linear_extrapolation"}`（`src/loop/driver.cpp`），`--models` 的解析先 `clear()` 再按逗号切分，所以**只有显式给一个值才会替换默认集合**；而空列表的表达方式是 `--models ""`（清空后不再 push）。同时这些世界模型**读真值**（`zero_delta` 直接遍历 `ws.entities()`），它们的主张几乎与真值重合，于是把平均匹配误差稀释到接近 0——**"默认带着两个神谕跑"与"指标失真"叠在一起**。
- **决策与理由**：实验设计改为**三组并列**（S1 显式 `zero_delta` 与 D3 发布配置逐字一致 / S2 省略 `--models` 走 CLI 默认 / S3 `--models ""` 纯感知），并在研究笔记里写明 S1 的 71% 账本条目来自读真值的模型。**不把"默认带两个世界模型"当成缺陷去改 CLI**：默认集合是文档化的演示配置，语义清楚；缺陷在于**实验作者容易以为"省略 = 关闭"**。因此纪律写进研究笔记与本日志：**任何"只跑感知"的实验必须显式写 `--models ""`，并在工件里核对阶段键**。
- **教训**：① **"省略参数"与"显式置空"在有默认值的 CLI 里是两件事**——凡是默认值非空的开关，实验文档必须写"如何关闭它"，而不是"不传它"。② **工件里的阶段键（`predict:<name>` / `detect:<name>`）是实验条件的自证**——写实验时应当把"检查工件里出现了哪些阶段键"当成固定动作，就像检查 `faults=0` 一样。③ 当**参与者能读到真值**时，它既是有效的对照（神谕基线），也是**指标污染源**；同一套指标要在"带神谕"和"不带神谕"两种条件下各跑一遍，否则读到的平均数可能完全是神谕的贡献。

## 017 · 绝对容差让判别力随目标尺度反向变化：聚合过线掩盖了层内不过线（2026-10-27，切片 D4）

- **现象**：判据 (c) 在真实面板上**聚合达标**（separation `0.305180 ≥ 0.30` → PASS），但按目标尺度分层后：**大目标层 separation `0.220196 < 0.30`**，小目标层 `0.357171`。两个评分空间在大目标层给出**完全相同**的 `0.220196`。
- **定位**：判定"正确"用的是**同一个绝对容差** `kCorrectTol = 0.1`（归一化单位，与目标尺度无关）。RT-DETR 对大框的框心定位**相对**误差更小 ⇒ 大目标层里诚实侧的正确率**上升**（ECE `0.2898`，高于小目标层的 `0.1428`），而注入侧的正确率几乎不动（`0.51` vs `0.50`）⇒ 分离量 = |诚实侧 ECE − 注入侧 ECE| 被压缩。**两个空间同值**这条证据把成因挡在评分空间之外——塌陷不是新机制引入的回归。
- **决策与理由**：主判据按 **L2 §5.2 写死的裁定条件**（全面板聚合）裁定 PASS：**阈值不动、不分层重裁**。但按 L2 §5.2"不允许只报聚合值"的硬要求，层内塌陷**与裁定并列陈述**，不藏在附注里。**修复方向未定**，如实登记为遗留：按目标尺度自适应容差会改 `kCorrectTol` 的语义 ⇒ **需新 ADR**；换带 track id 且许可可用的数据集 ⇒ Phase 4 数据侧立项。本片不假装它已被解决。
- **教训**：① **聚合达标 ≠ 处处达标**——同一个阈值在分层上可能一边高一边低，聚合值只说明"总体上过线"。判据一旦允许分层观测，就必须把**分层的失败形态与聚合结论并列陈述**。② **绝对容差是隐蔽的尺度依赖**："两个空间用同一个容差"是实现上的简洁，不是语义上的中立；容差的量纲（归一化 vs 目标尺度）必须随判据一起被审视。③ **"两个配置给出同一个数"是一条诊断信息**：它把故障定位到被比较对象之外，避免把结构性问题误判成新代码的回归。

## 018 · 手写分段并发下载器会静默产出"大小看起来对"的坏文件：尺寸校验不等于完整性（2026-10-27，切片 D5 Gate 0）

- **现象**：Gate 0 取 FFmpeg LGPL 构建与 cuDNN 9 时，本机网络**按连接限速**（单连接实测 5–31 KB/s，PyPI 单连接 5.2 KB/s），直接 `curl` 一个 500 MB 文件要几十小时。写了个 bash 分段并发下载器（`xargs -P` + 按 range 切片 + `cat` 拼接）后：① 一次跑 32 连接聚合 **≈300 KB/s**，178 MB 的 FFmpeg 包 9 分钟到手；② 但另一轮 502 MB 的 cuDNN 包**拼接结果短了 25 MB**，且"修复脚本"把 2 个本来完好的分片删掉、3 个分片写成半截——**产物静默损坏**。
- **定位**：三个独立缺陷叠在一起，每一个单独看都不致命：
  1. **总大小是猜的**。给脚本传的 `TOTAL` 用了 `480 MB` 的十进制/二进制换算值（503 316 480），真实大小是 502 799 547。**最后一个分片的 range 越过 EOF**，服务器按实际末尾截断 ⇒ 拼接结果天然短一截，而"检查 got == want"的判据本身用的是那个错的数。
  2. **后台子进程没被等**。脚本用 `bash cmds.sh &` 启动 40 个 `curl … &`，随后父脚本 `wait`——但这些 curl 是**孙子进程**，父脚本的 `wait` 对它们无效，于是在下载仍在写文件时就去拼接，把半截分片拼进产物（并且 Windows 报 `Device or resource busy` 才暴露出来）。
  3. **中途换了切片几何**。第一次用 `N=16`、重试时改成 `N=12`，两批分片写进**同一个 parts 目录**、同名不同偏移 ⇒ 拼接顺序与偏移全错。
- **决策与理由**：① **弃用"自己数字节"这条验收线**，一律以**发布方摘要**收尾：FFmpeg 那次能确认没问题，靠的是把 `sha256sum` 结果与 **GitHub Release API 的 `asset.digest`** 比对（逐位吻合）；cuDNN 以 **PyPI 的 `digests.sha256`** 为准。这与本仓库 `tools/fetch_*.mjs` 一直在做的事（**固定清单 + SHA256**）是同一个纪律——**我这次是在仓库之外另写了一套工具，把已有的纪律绕过去了**。② **BITS 也不是答案**：改用 Windows 自带的 `Start-BitsTransfer` 之后，它留下了一个**大小正好等于 Content-Length、但 150 MB 之后全为 0** 的文件（BITS 会预分配目标文件；作业并未卡死，而是**仍在传**——实测 `BytesTransferred = 82 451 474 / 502 799 547`，即 **16 %**，从未进入完成态）。抽查 6 个 1 MiB 采样区，**4 个是纯零**；`sha256` 与 PyPI 摘要不符。**"操作系统的工具"不能替代摘要闭环。**③ 最终形态：**分段并发 + 每片按 Content-Length 收口 + 全部 promise 被 await + 结尾与发布方摘要比对**，任一环节不过就判定不可信并保留现场。④ 临时脚本放临时目录，不进仓库；进仓库的只有 `tools/fetch_video_sample.mjs` + `tools/fetch_video_sample.manifest.json`（带许可与 SHA256）。
- **教训**：① **尺寸校验不是完整性校验，而且它比想象中更容易骗人**——BITS 的预分配文件"大小完全正确"却几乎没有内容。任何拼接式/异步取数都必须以 **publisher digest** 收尾，没有摘要可用时至少要**结构化验证**（能否作为 zip 打开、内部清单是否自洽）。② **不要消费在途作业的产物文件**：传输服务（BITS / 任何带预分配的下载器）的目标文件在完成前是"看起来完整"的，读它等于读一堆零。③ **别把"总大小"当已知量传进去**——它是单位换算里最容易混进 1000/1024 误差的一项；要么由 `Content-Length` 实测，要么由摘要兜底。④ **子 shell 后台进程的 `wait` 是假的**：`bash script.sh &` 之后再 `wait` 等不到 script 内部启动的进程；要么把子任务列在同一个 shell 里，要么显式等 PID 集合（Node 的 `Promise.all` 没有这个坑，这也是最终改用 Node 的原因之一）。⑤ **中途不要换分片几何**；换并发数就等于换偏移，必须清空重来。⑥ **仓库里已有的纪律对自己也生效**：`tools/fetch_*.mjs` 早就把"数据不入库 + 清单 + SHA256 + 许可"定成了规矩，临时工具同样要落在这个规矩里，否则就会造出"本地有个文件，但没人能重建它"的新债。
