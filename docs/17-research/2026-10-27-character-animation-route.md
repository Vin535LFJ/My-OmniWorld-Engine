# 角色动画路线立项（2026-10-27）

> **归属声明（先读这条）**：本文件**不是本引擎的 sprint 切片，也不是阶段 D 的一部分**。它记录的是**另一个项目**（视频 → 动作 → 角色 → 成片）的立项判断：能不能实现、算力够不够、什么会卡死它。
> 之所以存放在本仓库：立项讨论发生在本仓库的会话里，且本仓库的 `docs/17-research/` 是 sprint 外想法的登记处（[research-queue.md](research-queue.md)）。**一旦该侧项目有自己的仓库，本文件整体迁移**，不要在这里继续生长。
> 与本引擎的唯一交集在 §8，不构成引擎的路线承诺。

## 0. 结论（先看这四条）

1. **能实现。** 三层拆解（动作提取 / 角色驱动 / 合成渲染）是对的，每层都有成熟开源组件；风险不在"能不能"，在"生成层出来的质量与速度"。
2. **算力只在一层不够**：P2 角色生成（Wan2.2-Animate / MimicMotion / MusePose）。P0 姿态提取、P1 3D 重定向、P3 分割合成本机（RTX 4060 Laptop 8 GiB）就够，**不要为它们租卡**。
3. **双 T4 只够做"存在性验证"，不够做迭代**：Turing 无 bf16、16 GB×2 ≠ 2 倍速（无 NVLink、显存分片给不了吞吐）、Kaggle session 磁盘配额约 20 GB 量级放不下 Wan2.2 级别的完整权重。
4. **真正会卡死的不是算力，是三件小事**：可度量的验收指标缺失、动作层的"安全实验单位"（≤72 帧 @ 模型原生帧率）没定、**身体模型与权重的许可**（SMPL-X 是非商用研究许可）。

## 1. 问题拆解：三层，各自独立迭代

| 层 | 输入 → 输出 | 组件候选 | 换角色时是否要重做 |
|---|---|---|---|
| **L-动作提取** | 视频 → 关键点序列 / 3D 骨骼 / 动作参数 | MediaPipe Pose、DWPose、（3D）WHAM / 4D-Humans | **不重做**（换视频只需重跑） |
| **L-角色驱动** | 运动数据 → 角色逐帧姿态 / 生成视频 | 骨骼渲染、Blender 重定向、姿态引导视频生成 | **要重做**（换角色换路线） |
| **L-合成渲染** | 角色层 + 背景 → 成片 | SAM 2 分割、FFmpeg 合成 | 不重做 |

**这三层是本项目唯一值得长期投资的结构**（"运动数据层"是公共资产，见 §6）。任何"一个模型包办一切"的方案都要绕开这个分层：它会让换角色变成重做全系统。

## 2. 路线取舍：交付物是 C + D，不是 A/B/C 三选一

| 路线 | 角色 | 本项目的定位 |
|---|---|---|
| A 骨骼驱动 | 姿态估计 + 骨骼渲染 | **降级方案**：C 的质量不达标时的保底；也是验证动作层是否干净的体检工具 |
| B 3D 重定向 | 动捕 + 绑定 + 引擎渲染 | **长期答案**，但当前**缺 3D 角色资产**（海报 → 可绑定 3D 角色不是一次生成能完成的），且受 §5 许可红线约束 |
| C 参考图驱动生成 | 角色图 + 动作视频 → 视频 | **主线**，与"海报人物跳舞"的目标匹配度最高 |
| D 人物替换 + 合成 | 分割 + 替换 + 光照/背景 | **必做**，但要**提到生成之前**（见 §7） |
| E 2D 骨骼绑定 | 插画分层 + 2D 骨骼 | **降级方案**：只适合简单摆动，不适合复杂舞蹈 |

## 3. 算力账（逐层，不是逐项目）

| 层 | 本机 4060 Laptop 8 GiB | 需要什么 |
|---|---|---|
| 姿态提取（MediaPipe / DWPose） | 轻松，毫秒级 | 无需远端 |
| 3D 估计 + Blender 重定向 | 够（渲染可纯 CPU） | 无需远端 |
| **角色生成** | **不够**（权重 + 显存 + 时长三重不足） | 远端 GPU，见 §4 |
| 分割（SAM 2）+ 合成（FFmpeg） | 短片段够（SAM 2 显存随帧数增长） | 无需远端 |

> **结论一句话**：算力预算应该 100% 花在 P2；其余三层在本机做，且**先把它们做完**——它们便宜，而且它们决定了 P2 的输出能不能被评价。

## 4. Kaggle 双 T4：能解什么、不能解什么

### 4.1 能解

- **一次决定性实验**：3 秒（≤72 帧 @ 16 fps）、480p、单模型、单设定，跑通即回答"这条路能不能走通"。
- **并行两个候选做对照**：Wan2.2-Animate vs MusePose 跑同一段素材——这恰是双卡最有价值的用法。**双 T4 的正确用法是"并行两个实验"，不是"一个实验快两倍"。**

### 4.2 不能解

- **迭代速度**。若每段片子以小时计，30 小时/周的配额只够三到八次尝试——这不叫迭代，叫抽奖。
- **Wan2.2 级别的完整权重**。Kaggle session 磁盘配额在 20 GB 量级（以 UI 为准），而 Wan2.2 A14B 的权重是几十 GB 量级，除非逐块从 HF 拉取（脆弱）。**现实目标是 MimicMotion（1.3B UNet）或 MusePose 这类小得多的栈。**
- **多卡加速**。T4 无 NVLink，跨卡走 PCIe；diffusers 的 `device_map` 分片换来的是**显存余量**而不是吞吐，VAE/CLIP/T5 仍在单卡上。

### 4.3 T4 的三条硬约束（不是配置问题，是架构问题）

1. **Turing 没有 bf16**（bf16 自 Ampere 起）。Wan 系流水线默认 bf16，在 sm_75 上会直接报错，必须切 fp16 → **跑出来的数值分布不是官方 checkpoint 调优过的那个**，脸糊/肢体粘连这类现象要先怀疑 dtype 再怀疑模型。
2. **16 GB 显存**：必须 offload / 分块交换 / 降分辨率（480p~576p），且只吃短段。
3. **Kaggle 环境的可复现性差**：session 存储不持久（权重和素材每次重拉）、驱动版本由平台控制、镜像内容会漂。**任何产出数字的实验必须自带环境元数据**（镜像摘要 + torch/diffusers 版本 + 权重 revision + 分辨率/帧数），否则数字不可复现、不可引用。

## 5. 许可红线（比算力更可能致死）

| 组件 | 许可状态 | 结论 |
|---|---|---|
| **SMPL-X / SMPL 身体模型** | **非商用研究许可**，商用需另行授权 | **商用即硬门**。命中路线 B 与 MusePose（要渲染网格） |
| MediaPipe / DWPose 代码与权重 | Apache-2.0 系 | 可用 |
| SAM 2 代码与 checkpoint | Apache-2.0 | 可用（显存随帧数增长） |
| MimicMotion / MusePose **权重** | **仓库协议 ≠ 权重协议**，必须逐个查 HF model card | 未查清前不得进任何可交付路径 |
| Wan2.2 代码与权重 | Apache-2.0 | 可用（但体积见 §4.2） |
| FFmpeg | LGPL 纪律：**禁 `--enable-gpl`**、动态链接、保留声明 | 与本仓库同一条红线 |
| Blender | GPL，但作为**外部工具**调用不触发链接红线 | 可用 |

> 纪律与本仓库一致：**许可未核验通过的东西不进可交付路径**；核验结论要落到书面记录，不是"我记得它是 XX 协议"。

## 6. 唯一值得长期投资的资产：运动数据层

上层可以换角色、换渲染方式，只有这一层不该重写。它至少要冻结：

| 字段 | 语义 | 为什么要有 |
|---|---|---|
| `timestamp` / `frame_index` + **时间基准** | 逐帧运动对应视频的哪一刻 | 源视频 30 fps、模型原生 16 fps → 不显式定时间基准，动作会整体变速且没人察觉 |
| 关键点（2D/3D） + **每点置信度** | 姿态估计的原始输出 | 低置信度必须能被下游丢弃，不能被插值掩盖 |
| **身体朝向** | 正面/背面/侧面 | 决定重定向与分割策略；也是"人物识别"与"背景误检"的区分依据 |
| 关节角度（可选派生） | 便于骨骼渲染直接消费 | 避免每个渲染器各算一遍 |
| **运动质量标记** | 抖动 / 遮挡 / 出画 | 让下游能拒收坏帧，而不是渲染出扭曲动作 |

> 这一层与本引擎的 World Contract 同构（identity / time / ownership / confidence）。若侧项目成规模，它应当有自己的契约文档与单写者规则，而不是散落在各处的脚本参数。

## 7. 执行顺序（按算力约束重排，与"先做最难的"相反）

```
P0   姿态提取（本地，零成本）           → 能不能准确提取动作？
P0.5 运动数据层落地 + 数值验收           → PCK / MPJPE / 抖动指标 / 身份余弦   ← 唯一真正的公共资产
P1.5 背景与合成先行（SAM 2 + FFmpeg）    → 能不能单独评估"角色层"，而不是看混了背景的成片
P2   一次决定性生成实验（Kaggle 双 T4）  → 角色外观与复杂动作能不能保住？只跑一段
P1   3D 重定向（仅当 P2 明确不达标）      → 可重复、可编辑的长期解
```

**P1.5 提前的理由**：没有它，P2 的输出只能整段肉眼看，无法归因——"动作对了但脸糊了"和"动作错了"会混在一起。这是能否科学迭代的分界线。

**验收必须可度量**（否则每轮都是"看着还行"）：

- **姿态跟随误差**：对生成帧再跑一次姿态估计，与驱动骨架比 PCK / MPJPE。
- **身份一致性**：海报人脸 crop 与生成角色人脸 crop 的嵌入余弦（ArcFace / CLIP）。
- **时序抖动**：关键点二阶差分的抖动量。

## 8. 与本引擎的关系（不构成承诺）

角色动画管线天然是"视频理解 + 视频生成"的组合，**形态上像本引擎的一个未来参与者**（感知适配器 + 评测面板）。但：

- 它**不在**阶段 D 的路线上，本引擎的「不碰」清单仍然有效（训练模型、GPU 渲染器、生成式后端都不在本阶段）；
- 阶段 D 的 D5（GPU 数据流与零拷贝）如果落地，**恰好是这类"视频 → 推理"管线的公共底座**（解码 → 推理全程显存驻留 + 可计量的拷贝计数）；
- 真要接入，需要另立 ADR，而不是在本文件里顺手约定。

## 9. 未决问题（下一步要回答的）

1. **是否商用？** ——直接决定 SMPL-X/部分权重是不是硬门（§5）。
2. **目标成片规格**（时长 / 帧率 / 画幅 / 是否要原视频背景）——决定 P2 的模型选型与段长策略。
3. **能否接受"生成层失败则降级到 A/E"**——决定要不要投入 B（3D 资产从哪来）。
4. **Kaggle 权重获取路径**（HF 直连 vs Kaggle Dataset 挂载 vs 先在别处转存）——决定 P2 实验的可重复性。
5. **侧项目落在哪个仓库**——本文件暂存于此，待定后整体迁移（见文首归属声明）。
