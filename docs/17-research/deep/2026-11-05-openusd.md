## 0. 摘要（给赶时间的人）

OpenUSD 是 Pixar 三十余年"组合场景描述"体系的第四代开源形态（Marionette → Presto → TidScene → USD，2012 立项，血统叙述见 [G2]），本质是三件事的叠加：**数据模型**（Layer/PrimSpec/opinion，持久化在 .usda/.usdc 文件中）、**组合引擎**（Pcp：六种 composition arcs 按 LIVERPS 强度序把每个 prim 的所有意见源索引成一棵 prim index）、**求值视图**（Stage 上按 strong-to-weak 做 value resolution），外加把渲染解耦出去的 Hydra 框架。

**核心原理一句话**：把"场景"表示为分布在多个持久层中的意见（opinion）集合，组合引擎把"这个 prim 的意见可能来自哪里"预计算成一个有序图（prim index）并缓存，值解析沿该图从强到弱取第一个有效意见——非破坏性协作由此变成一个确定性、可复现的纯求值问题。

最关键的三个机制：① **LIVERPS 组合算法 + prim index 缓存**（官方原话：每步都重算"would be very costly"，所以 per-prim 预计算缓存 [G1]）；② **change processing——authoring 是唯一事件**（编辑→依赖图驱动的精确失效→UsdNotice 通知，无任何自驱动演化 [G1][C1]）；③ **Hydra 的 pull 式成像**（RenderIndex + ChangeTracker 脏位驱动，Sync/Prepare/Commit/Execute 四阶段，"only pulls data when it is needed" [S2]）。

对本项目的意义：OpenUSD 用**强度序隐式仲裁**多作者冲突（每字段可有多作者、LIVERPS 决定谁赢、败者意见不留痕），OmniWorld 用 **tick 账本显式留痕**（每字段单一作者、全部意见进 Belief Ledger 对账）——两者是同一问题（多源场景/状态融合）的两个正交解。它"不是运行时"的机制原因（§2.7）恰恰证明了 OmniWorld 的立足空间：演化驱动、所有权、置信度是它设计上让渡出去的。

## 1. 项目定位与生态位

**归宿：External reference（资产组织参照），不是引擎，不是竞品**——定位裁定、反模式边界、one-way export 计划见事实卡 [§6](../projects/openusd.md)；本报告只补一句原理层的理由：OpenUSD 的全部工程密度都花在"**把多源作者意图确定性地折叠成一个视图**"上（组合引擎 + 值解析），而活世界运行时的工程密度花在"**让视图随时间自洽地演化**"上（调度、裁决、置信度）——前者是后者的*组织层输入*，不是替代品。USD Fabric（NVIDIA 侧的 GPU 运行时内存布局）与 OpenUSD 的关系已在事实卡 [§2.2](../projects/openusd.md) 裁定（未证实数值主张互链不复制），本报告 §2.7 有对应的机制性佐证。

## 2. 原理详解

### 2.1 架构总览：四层库分工与一条数据流

OpenUSD 不是单块，而是按职责严格分层的库族（本节分层与各层"不管什么"均出自官方模块 overview 文档 [C1][C2][C3]）：

```
┌─ 应用层：usdview / DCC 插件 / 自研客户端
├─ UsdImaging + Hd（Hydra）：组合结果 → 渲染器抽象       [C3][G4][S2]
├─ Usd：Stage / UsdPrim / schema / value resolution       [G1][C6][C7]
├─ Pcp（Prim Cache Population）：组合引擎（prim index）    [C1][C4][C5]
├─ Sdf（Scene Description Foundations）：层 / prim spec / 序列化  [C2]
└─ 基础设施：Tf（通知/调试）、Ar（asset resolution 插件点）、Vt/Gf（值与数学）
```

三层职责的官方原话划界（这三句是理解整个系统的钥匙）：

- **Sdf 层不知道组合**："SdfLayer objects do not have the context to know how they relate to other layers"（[C2]）——层只是 opinion 的持久容器，一切"谁覆盖谁"的语义都在上层。
- **Pcp 层不产出 scenegraph、不做值解析**："Pcp does not maintain a scenegraph of composed objects"，且官方明确把 "value resolution"、"scenegraph structure, objects and their identity" 列为 Pcp 之外的事（[C1]）——Pcp 只回答"这个 prim 的意见可能来自哪些 (LayerStack, path) 位点、强度序如何"。
- **Usd 层只缓存 prim 级信息**：Stage "caches in memory just enough information about the composed namespace and backing files"；"Prims, along with their associated, computed indices, are the only persistent scenegraph objects that a Stage retains in memory"（[G1] Stage/Prim 词条）——属性级组合值一律不预存，按需解析（§2.4）。

**主数据流**（authoring → 消费）：

1. 各作者/部门把 opinion 写进自己的 SdfLayer（edit target 决定写到哪一层，§2.2）；
2. 打开 Stage 时 Pcp 递归解释六种 composition arcs，为每个 prim 生成并缓存 **prim index**（§2.3）；
3. 客户端沿 prim index strong-to-weak 做 **value resolution** 拿到最终值（§2.4）；
4. 任何层被编辑 → **change processing** 精确失效受影响的 prim index → 重新组合 → `UsdNotice` 通知订阅者（§2.5）；
5. 渲染侧由 Hydra 从组合视图（或任意 scene graph）pull 数据成像（§2.6）。

血统与并行姿态：USD 交付时"introduced parallel computation into all levels of the scene description and composition core"（[G2]），Presto 组合引擎血统 + TidScene 惰性时间采样数据模型的合流是 USD 的立项动机（[G2] Heritage 节）——这一点在 §2.7 是关键证据。

### 2.2 数据模型：Layer / PrimSpec / Opinion（Sdf 层）

**怎么做。** Layer 是"the atomic persistent container of scene description"，内含零或多个 PrimSpec；`SdfLayer` 既是层的 document model 又是读写接口，实际编码靠 `SdfFileFormat` 插件（usda 文本 / usdc crate / Alembic 等皆由此接入）（[G1] Layer 词条）。PrimSpec 是"uncomposed prim in a layer"，**稀疏**：一个描述 Cylinder 的 PrimSpec 可以只有 radius 没有 height，缺的部分由其他 PrimSpec 或 schema fallback 补（[C2]）；属性分 `SdfAttributeSpec`（值）与 `SdfRelationshipSpec`（多目标"指针"）。Opinion 是"value resolution 的原子参与元素"：每次 author 一个值，就是在某层的某 PrimSpec 上为该对象表达一个 opinion；组合后同一对象可被多层多重 opinion 影响，次序由 LIVERPS 决定（[G1] Opinions 词条）。寻址统一用 `SdfPath` 层级命名空间（含 variant 路径语法 `{modelingVariant=withCargoRack}`）（[G1] Path 词条）。

二进制 crate 格式（.usdc）为随机访问而生：打开时只读文件索引"deferring access to big data until a client requests it specifically"；"lockless data extraction for high-bandwidth multi-threaded reading"；mmap/pread 双模式可配；为冷缓存网络访问把开文件所需数据压进连续 footer；**编辑是追加式**，废弃值残留需 `usdcat` 重写回收（[G1] Crate File Format 词条）。Session layer 是每 Stage 可选的"scratch space"，承载"application state"（usdview 的 variant 选择、visibility、activation 都写进去），`UsdStage::Save` **不保存** session layer（[G1] Session Layer 词条）。

**为什么这样设计。** 层 = 协作与审计的单位：subLayers 让多部门"each artist to work in their own file... without erasing or editing any other artist's work, and helps to provide a clear audit trail"（[G2]）；稀疏 PrimSpec + fallback 让场景描述"sparse and compact, and allows for self-documenting behavior"（[G1] Fallback 词条）；crate 的惰性+无锁是"低延迟随机访问"这个全系统目标（§2.4）在文件层的投影。

**代价是什么。** ① 文本 usda 必须"read in their entirety, parsed, and stored in-memory as soon as they are opened"，只有 crate 具备增量 flush 能力（[G1] Layer 词条）；② crate 反复编辑膨胀（追加式写的代价）；③ 层与层之间无上下文（[C2]）——意味着任何跨层语义（覆盖、变体、引用）都无法在文件层表达，必须付出组合引擎的计算；④ opinion 只存在于层中，"Data authored to layers... will remain in memory until SdfLayer::Save is called"（[G1]）——持久化是显式动作，不是自动的。

### 2.3 组合引擎（Pcp）：六弧、LayerStack、LIVERPS 与 prim index

**怎么做——弧的语义。** Composition arcs 是"operators"，命名成"弧"因为画 prim index 图时它们就是连接位点定向边（[G1] Composition Arcs 词条）。除 subLayers 外全部 **list-editable**（sparse prepend/append/delete/reset），于是"非破坏地改变场景的大尺度结构"成为可能（[G1] 同词条）：

- **SubLayers**：构建 **LayerStack** 的弧。LayerStack 定义 = "The ordered set of layers resulting from the recursive gathering of all SubLayers of a Layer, plus the layer itself as first and strongest"（[G1] LayerStack 词条）；组合对 sublayer 树做深度优先遍历，根层最强（[S1]）。两条关键规则：**组合弧以 LayerStack 为目标，不是单层**；LayerStack 是 list-editing 的作用域容器（[G1] LayerStack 词条，sequenceFX/shotFX 例子演示跨层 delete references）。
- **References**：跨资产聚合的主弧——把另一个 LayerStack 中某 prim 的组合结果"封装"后重命名挂到当前命名空间；同名 prim 靠改名避免冲突；层文件只打开一次共享（prim 不共享，除非 instancing）；可携带 Layer Offset 缩放/平移时间（[G1] References 词条）；引用 sub-root prim 有 variant 选择权丢失等"surprising behavior"（[G1] 同词条）。
- **Payloads**：一种特殊 Reference——"deferred reference"：`LoadNone` 打开 Stage 时"recorded, but not traversed"，客户端手动构造 working set；强度上**弱于 references**（[G1] Payload 与 Load/Unload 词条）。load/unload 是运行时标志，"loading/unloading a payload doesn't author any changes to layers"（[S1]）；Pixar 实践是"lofting"——把必须常驻的轻量接口层放在 payload 之外（[S1]）。
- **Variants/VariantSets**：资产内打包备选集合；variant selection 本身是场景描述的一部分（可被更强层覆盖），variant 内部"can also include additional composition arcs"（[G1] Variant 词条）；无 authored selection 时可由插件/应用提供 fallback（[G1] Variant 词条）。
- **Inherits**：广播编辑——"non-destructive 'broadcast' operator"，源 prim 的**全部**层级场景描述流向所有继承者；与 references 的本质差别："references fully encapsulate their targets... whereas the relationship between inheritors and their inherits target remains 'live' through arbitrary levels of referencing. In other words, when a prim *inherits* from another prim, it **subscribes itself and all referencing contexts to changes made to the inherited prim**"（[G1] Inherits 词条）——inherits 是订阅关系，reference 是复制快照。
- **Specializes**：行为像 inherits 但强度规则相反——"any opinion expressed directly on the specialized prim will always be stronger than any opinion expressed on the base prim, **in any referencing context**"（[G1] Specializes 词条）；为材质库精化而生（Pixar 首个用例即 shading schema 的材质特化，[G1] 同词条；[S1] 演示 GlossyPaper 例子）。
- **Relocates**：以层元数据记录 source path → target path 映射，在"不能直接编辑组合源 prim"的场景下非破坏地改名/重挂；属性路径不可迁移；被迁走的源路径视为失效，保证"exactly one location... to express opinions"（[G1] Relocates 词条）。

**怎么做——LIVERPS 强度序。** 官方全称是 **LIVERPS** = Local, Inherits, VariantSets, Relocates, References, Payload, Specializes（[G1] LIVERPS 词条；业界常写 LIVRPS，同一序）。算法是逐属性/元数据的查找规程：依次查 Local（本地 LayerStack 全部层）→ Inherits → VariantSets → Relocates → References → Payloads（已加载才走）→ Specializes，找到即停。三条递归规则是精髓：① 前五种弧递归时应用 **LIVERP（无 S）**——"we ignore Specializes arcs while recursing"；② Specializes 递归时应用**全 LIVERPS**；③ "ancestral arcs are weaker than direct arcs"（祖先弧弱于直接弧，[G1] Direct Opinion 词条）。代码佐证完全一致：`PcpArcType` 枚举注释"**The following arcs are listed in strength order**"，顺序 Root/Inherit/Variant/Relocate/Reference/Payload/Specialize（[C4]）；弧内部再按 `siblingNumAtOrigin` 排序——"index among sibling arcs at origin; lower is stronger"（[C5]）。注意：**LIVERPS 是 LayerStack 内部的序**，多个 LayerStack 之间靠弧的嵌套递归归约——"This ordering is recursive"（[S1]）。

**怎么做——prim index。** Pcp = "Prim Cache Population"（[C1]），负责求值全部组合弧，产出 **prim index**："an ordered (from strongest to weakest) list of 'Nodes'，即所有贡献 opinion 的层内位点，外加每个位点是经哪条弧'编织'进来的"（[G1] Index 词条；课程讲义的表述：节点是 (layer stack, path)，边是组合算子，[S1]）。命名空间本身（"什么 prim 存在、在哪"）也按 LIVERPS 配方计算但"slightly more involved"（[G1] LIVERPS 词条）。入口 API：`PcpCache::ComputeLayerStack()` 与 `PcpCache::ComputePrimIndex()`（[C1]）。Instancing 是 index 级的剪枝：`instanceable=true` 且带组合弧的 prim，Stage "prune its prim composition at the instanceable prim"，以 (目标层 + 所用弧) 为"instancing key"只为每个唯一 key 完整组合一次 prototype——"explicit instances, with implicit prototypes"（[G1] Instancing 词条）。

Pcp 还有三个常被忽略的机制性设计：**错误是一等公民**（PcpErrorBase 子类携带语义细节，作为组合输出缓存返回，"Pcp does not embed any error handling or reporting policy"，[C1]）；**依赖注册表**（每个缓存计算记录其依赖——如引用——供变更传播与 namespace editing 使用，`PcpCache::GetPathsUsingSite()` 可反查，[C1]）；**path translation**（组合弧把 opinion 绑到新命名空间位置时，关系目标等路径自动重绑定，"one of the more subtle and important behaviors of Pcp"，[C1][G1] Path Translation 词条）。

**为什么这样设计。** ① **Index 缓存**是整个体系的性能支点，官方原话："Performing every step as described above for each value lookup would be very costly. This is why we compute and cache an Index for every prim on the Stage."（[G1] LIVERPS 词条）——把"重解释所有弧"的成本一次性付清，之后每次取值只是走有序位点表。② **封装（reference）与广播（inherit）是两种编辑拓扑的刻意分化**：前者隔离资产、后者保持订阅——同一资产被引用一千次时，改一处 `_class_` prim 即可全量生效而不触碰资产文件（[G1] Inherits 词条 Forest.usd 例子演示 inherits 穿透引用链、references 则不能）。③ **Specializes 的"全局最弱"解决 inherits 的覆盖污染**：课程讲义的 GlossyPaper 例子里，若用 inherits，对基材质 Paper 的更强层覆盖会连带覆盖掉本应更精化的 GlossyPaper；换成 specializes 后"we get exactly the behavior we want"（[S1]）——强度序上把"兜底意见"钉死在所有人的下面，精化链才不会被外部覆盖打穿。④ **Payload 的"延迟"把组合成本变成可选项**："pay runtime cost only for the features you need to use"（[G1] Instancing 词条 "Pay for what you need" 段）。

**代价是什么。** ① Inherits 的订阅是常驻成本："There is a runtime cost to keeping inherits live, so you may want to avoid proactively adding inherits everywhere"（[G1] Inherits 词条）；② Instancing 换性能的代价是放弃 instance 子树内任何 prim 的独立覆盖（"we give up the ability to uniquely override opinions on prims beneath the 'instance root'"，[G1] Instancing 词条）；③ 组合成本随层文件数与引用深度增长——官方性能指南专节"Monitor Layer count"，并给出量级感："Large scenes can take seconds or minutes to open, but typically the Model Hierarchy view can be opened in under a second, or a small number of seconds"（[G3]，payload 分层打包是官方建议结构）；④ Relocates 的表达力边界（仅 prim 路径、源路径失效规则，[G1]）；⑤ 错误不自动处理，策略全在客户端（[C1]）。

### 2.4 Value Resolution：从 prim index 到最终场景值

**怎么做。** 官方用三条对比把"组合"与"值解析"切开（[G1] Value Resolution 词条，全段为机制核心）：

1. **"Composition is cached, value resolution is not"**——组合结果按 prim 缓存；属性级组合值**不**预计算，"aimed at keeping latency low for random-access to composed data, and keeping the minimal memory footprint for USD low"；需要重复查询时客户端可 opt-in `UsdAttributeQuery`/`UsdResolveInfo` 自建缓存。
2. **"Composition is internally multi-threaded, value resolution is meant to be client multi-threaded"**——打开大 stage 是大计算、核心内部并行；值解析刻意轻量，官方对多核的指导是"perform as much simultaneous value resolution and data extraction as possible"——"USD's design was guided by this access pattern"。
3. **"Composition rules vary by composition arc, value resolution rules vary by metadatum"**——解析只消费有序位点表，对产生它的弧无感知；但"怎么合"取决于被解析的东西。

逐类型规则（[G1] Value Resolution 词条）：**metadata** 基本规则是 strongest opinion wins（specifier/typeName 等有特殊规则）；**字典逐元素合并**（更强层的 `customData["keyOne"]` 与更弱层的 `customData["keyTwo"]` 合成一个字典，不互相屏蔽）；**relationships** 因 list-editing 必须**合并全部**意见（弱到强应用，规则在 `SdfListOp::ApplyOperations`）；**attributes** 最特殊——沿 prim index 的每个位点依次检查**四个值源**：TimeSamples → Splines → Default → Value Clips（schema 定义的属性还有第五源 **fallback**，以及 attribute block 在请求时间坐标上的屏蔽）。时间维度上：`UsdAttribute::Get(time)` 受 Layer Offset 影响（offset/scale 逐弧**乘法可组合**：A→B 2.0、B→C 3.5 ⇒ 总 7.0，[G1] Layer Offset 词条）；请求点落在两个 TimeSamples 之间时默认线性插值、失败则 hold 前值，Spline 则按曲线段插值（[G1] + [T1]）。代码佐证：`Usd_Resolver`——"Given a PcpPrimIndex, this class facilitates value resolution by providing a mechanism for walking the composition structure in **strong-to-weak order**"，`NextLayer()` 在当前 LayerStack 内走更弱层、走完跳下一个更弱 PcpNode（[C6]）。

组合的 prim 状态（active/loaded/abstract/defined/instance/has-payload 等）在 `Usd_PrimData` 的 flag 位里缓存，供遍历谓词快速过滤——"all cached, for fast access"（[G1] Stage Traversal 词条；flag 位清单见 [C7]）。

**为什么这样设计。** 核心是访问模式的取舍：创作管线里"随机抽查某个属性"远比"全场景批量重算"高频，所以把贵的（组合）缓存、把轻的（单值解析）留作按需——同一段官方文字直接给出动机（§上引 [G1] 三条对比）。时间不是独立子系统：TimeCode 是"unit-less time coordinate"（double 编码，可编码 Default 值坐标；真实秒换算靠根层 `timeCodesPerSecond` 元数据，[G1] TimeCode 词条），时间映射寄生在弧（Layer Offset）上——组合树本身就是时间的映射树。

**代价是什么。** ① **动画值不能跨源合并**——官方用户指南原话："You can't 'compose' partial animated values, or 'sparsely' override animated values"：两个引用分别带不同时间段的 timeSamples，组合后**只有更强 opinion 的整段时间线生效**；要合并只能用 Value Clips（把 timeSample 覆盖切分进多文件、像非线性剪辑一样拼接，[T1] note + [G1] Value Clips 词条）——强度序优先于时间轴，这是理解 USD 动画管线最容易踩的机制性坑。② 解析不缓存 = 高频访问同一属性的客户端必须自己上缓存设施（opt-in API 是官方承认的补偿，[G1]）。③ fallback 依赖 schema registry 的加载与 prim definition 计算（[G1] Prim Definition 词条）。

### 2.5 变更与失效：change processing——authoring 是唯一事件

**怎么做。** 官方 Change Processing 词条给出三条铁律（[G1] Change Processing 词条）：① **总是激活**："Whenever you use the Usd or Sdf APIs to mutate any layers that contribute to a UsdStage's composition, that stage will update itself immediately, in the same thread in which authoring was performed"（change processing 自身可起 worker 线程）；② 完成后发 `UsdNotice`，且**建议客户端不要立即更新**："note what has become out-of-date (dirty), and defer updating until necessary"——官方明说这是为高频编辑场景省工作量；③ **编辑期间单写者、零读者**："only one thread at a time may be editing any of those layers, and no other thread can be reading from the stage while the editing and change processing are taking place. This is because we do not want to weigh down read access to UsdStage data with any kind of locking."

Pcp 侧的对应机制（[C1]）：`PcpChanges` 两阶段——先**追依赖**建变更清单（"including chasing dependencies to find all the affected caches"），再**应用**（失效内部缓存）；之后"It is up to the client to re-pull on any affected caches"；`PcpLifeboat` 在失效与重拉之间保住被引用数据不被释放。prim 可能被 re-index、消失或新生（[G1] 同词条）。

**为什么这样设计。** 读不加锁是多线程读性能的前提，代价被转嫁给写路径（编辑串行化）；失效的**精确性**靠 Pcp 依赖注册表（§2.3），不靠全量重算；通知只报"什么脏了"不代劳更新，把失效传播的时机选择留给消费者（Hydra 正是按此纪律把脏标记攒到下一次 Execute 才消化，[S1][S2]）。

**代价是什么。** ① 编辑热路径串行——频繁高频写 + 并发读的工作负载不是它的目标形态；② 失效传播对客户端是纪律而非保证（收到通知不 defer 就自找性能问题）；③ **没有事件调度器**：能触发重算的事件只有"authoring"一种——与 OpenExec 的定性互为表里："value-driven computation system, as opposed to being event-driven"（[G5]，事实卡 §2.1 已核，互链不复制）。这就是它"不是运行时"的第一块机制基石（§2.7）。

### 2.6 Hydra：渲染如何从组合结果成像

**怎么做。** Hydra 的官方自我定义（课程讲义）："**an open source framework to transport live scene graph data to renderers**"——项目最初是"用 OpenGL 尽快成像 USD stage 的高性能渲染引擎"，后来"we have abstracted away both! OpenGL and USD"（[S2]）；hd 模块 overview 的一句话版本："Hd is a framework that enables the communication between multiple scene graphs and multiple renderers"（[C3]）。

三个核心组件（[S2]）：**RenderIndex**——"flat representation that manages correspondence between scene description and rendering resources"（扁平的 prim 表，可查询）；**SceneDelegate**——把"场景数据访问"抽象出去；**RenderDelegate**——把"渲染"抽象出去。由此得到两张解耦图：多个场景源（USD 场景图、Presto 场景图）可同时喂一个 Hydra，多个渲染器（rasterizer / path tracer）可同时挂一个 Hydra。Hydra prim 三类：Rprims（renderable：mesh/curves/points/volume）、Sprims（state：camera/light/material/coordinate system）、Bprims（buffer：texture/buffer/field）（[S2]）。

执行模型（[S2]，全部为讲义原句或直接转述）："**Hydra is a pull system, but not just that, it only pulls data when it is needed**"；**ChangeTracker**"notify the render delegate when its information is not up to date anymore"；`HdEngine::Execute` 四阶段——**Sync RenderIndex（从场景源 pull 数据，可多线程）→ Prepare（resolve prim dependencies）→ Commit（提交 GPU）→ Execute（渲染）**；task 列表驱动（render task、color correction task 等）；渲染 delegate 可选用 **HdRenderThread**（2018 引入）把渲染挪出 Hydra 线程做 progressive rendering；内存侧"anywhere Hydra uses a VtArray, we have zero copy behaviors"+ foreign data source 适配 + 变更需 copy-on-write。课程 tiny sample 一行注释浓缩了整个事件观："**Change time causes invalidations, and generate image**"——时间变了 → 失效 → 重新 Execute，没有任何东西自己动。

与 USD 的接合点是 UsdImaging（USD 的 SceneDelegate/scene index 实现），扩展点为 **prim adapters**——"Prim adapters allow for associating a type to code that can populate data for Hydra to interpret"（[S2]）。**Hydra 2.0** 把这套接合升级为统一的 scene index 协议：两大抽象是"the scene index which provides a view of a scene and the scene index observer which takes a scene index as input and is informed about scene changes"；filter 是"both a scene index observer and a scene index"；`UsdImagingDelegate` 被 `UsdImagingCreateSceneIndices` 创建的 **scene index 链**取代（起点 `UsdImagingStageSceneIndex`，支持 API schema adapter 与单 USD prim 展开为多 Hydra prim 的 subprims）；`HdRenderIndex` 被"the scene index graph"取代；旧渲染 delegate 自动包装兼容；关键不变量：PrimsAdded/PrimsRemoved 消息必须与 `GetChildPrimPaths()` 遍历结果一致（[G4] Hydra 2.0 Getting Started Guide；接口定义见 [C8]：`HdSceneIndexPrim` = primType + container data source，"A prim is represented by a container data source which contains a tree of properties"，GetPrim/GetChildPrimPaths 均要求线程安全）。默认切换时点：AOUSD 公告 v25.11——"Building on the work in v25.08, UsdImagingSceneIndex is now enabled... This makes the Hydra 2.0 scene index code path the default for UsdImaging."（[A2]）。官方发行版随附 Storm（实时 rasterizer）、HdPrman（RenderMan）、HdEmbree（示例代码）三个 render delegate（[S2]）。

**成像管线中的位置**：`UsdStage（组合+解析后的场景视图）→ UsdImaging scene index 链（含 instancing/draw mode/selection 等 filter）→ HdMergingSceneIndex → renderer 专属 filter → terminal scene index → HdRenderDelegate → 图像`（[G4]）；viewport 与 final frame 共用同一框架（"Our goal is to support both viewport and final frame rendering"，[S2]）。组合（Pcp/Usd）与成像（Hd）完全正交：Hydra 核心不依赖 USD——这正是任何场景源（包括 NVIDIA 的 Fabric 类系统，推断，见 §2.7）都能接进 Hydra 的结构原因。

**为什么这样设计。** 双解耦（场景源/渲染器）把"渲染器即插件"变成结构性质，Pixar 自己就是第一个受益者（Presto 场景图与 USD 场景图并存）；pull + 脏位模型让"谁需要什么数据、什么时候拉"完全由渲染器自决，Hydra 只保证一致性与并行 pull 的基础设施（[S2]）。

**代价是什么。** ① Sync 期间场景 delegate 的 Get* 会被多线程并发调用——场景源必须自己保证线程安全与数据就绪（[S2] "These methods can be called from multithreading code"）；② prim adapter/scene index 双轨过渡期存在 legacy 包装层（HdRenderDelegateAdapterRenderer 等，[G4]），生态仍在迁移；③ Hydra 不解决"USD 属性解析慢"的问题——它只是纪律良好的消费者（defer-dirty + 按需 pull），USD 侧解析成本原封不动转给它（§2.4）。

### 2.7 它为什么"不是运行时"——四条机制性原因

先把官方的两面陈述摆平：intro 页一边说 USD 内嵌 "a high-performance **runtime** evaluation engine, embodied in a compact scenegraph known as a Stage"（[G2]），一边专设"Not a rigging system"一节（[G2]）。两个说法并不矛盾：USD 确实是**组合求值的运行时**，但它不是**活世界的运行时**。机制上由四条构成，每条都能指回来源：

1. **状态语义：持久状态只有 authored opinions，Stage 只是缓存视图。** 一切"事实"都存在于层文件里、以"某作者在某 prim spec 上表达过某 opinion"的形式记录；Stage "caches in memory just enough information"（[G1] Stage 词条）——它是派生物，可以随时重建。系统里**没有任何独立于作者意图的状态转移**：要让场景变，唯一途径是再次 author，然后 change processing（§2.5）。活世界运行时需要的恰恰相反：一个不被"作者"驱动、按自身规律（物理/规划/tick）演化的权威状态。
2. **事件模型：编辑是唯一事件，计算是值驱动的。** Change processing 只在层被 mutate 时触发（[G1]）；OpenExec 明确自我定性为 value-driven、非 event-driven，"authoring is the only 'event' that can induce recomputation"（[G5]，事实卡已核，互链）；没有 tick、没有循环、没有调度器概念——官方概念词汇表（Stage/Layer/Opinion/弧/TimeCode）里不存在对应物（对照 [G1] 全词条）。Hydra 同构：失效→按需 pull（§2.6），"only pulls data when it is needed"（[S2]）。
3. **数据访问取向：为"消费烘焙数据"而生。** 官方原话："USD's scenegraph leans towards a 'low-memory footprint, higher-latency data access' tradeoff, whereas a high-performance rigging system requires more of a 'high-memory footprint, low-latency access to data' tradeoff"（[G2] Not a rigging system）；且官方承认客户端可以"build more extensive in-memory caches on top of a UsdStage to provide lower-latency access"（[G2] 同节）——这个官方留出的生态位正是 Fabric 类 GPU 常驻布局的存在理由。血统叙事同样直白：Pixar 在 2008-2009 把管线从"animation and rigging were kept live up until rendering"切换到"animation and rigs were baked out into efficient 'pose caches'"，USD 的立项使命就是"marry the composition engine and low-level data model from Presto with the **lazy-access, time-sampled data model** and lightweight scenegraph from TidScene"（[G2] Heritage 节）——**它的时间语义是 TimeCode 采样坐标，不是因果时钟**（[G1] TimeCode 词条）。机制佐证：本次以 `grep '"path": *"pxr/usd/usdrt[^"]*"'` 检索 OpenUSD dev 分支完整文件树（tree.json，5,080,242 字节），**无任何 usdrt 路径**——USD Fabric 不是 OpenUSD 的一部分（互链事实卡 [§2.2](../projects/openusd.md) 的裁定与全景报告 [F2] 的未证实数值主张，此处不复制）。
4. **契约语义缺失：没有 ownership/confidence 的位置。** 组合天然允许"每字段多作者、由 LIVERPS 隐式裁决胜者、败者意见照常留存在各自层里"，这套仲裁**不需要也不产生**"谁对字段拥有唯一写权"的概念；也没有任何标量置信度参与解析。OmniWorld World Contract 的 ④所有权/⑦置信度在 OpenUSD 中没有对应物（对照 [00-总体设计.md §2](../../design/00-总体设计.md)；事实卡 §2.2 已裁定，互链）。

**结论**：OpenUSD 是"**场景描述 + 确定性组合求值 + 交换语义**"层——它把"谁在什么时候有权改什么（裁决）、演化由什么驱动（调度）、状态可信到什么程度（置信度）"整体让渡给宿主。这不是缺陷而是分工：正因为把这些让渡了，它才能成为跨 DCC 的最大公约数（[G2] Not a rigging system 末段给出的理由：加执行语义会让跨厂商交换变难）。

## 3. 能力边界与工程现实

官方承认的边界（rigging/执行语义、物理只到 schema、Core Spec 排除域词汇、无 GUID、usd-core 无 imaging 等）与硬件/许可事实**一律互链事实卡 [§2/§3/§4](../projects/openusd.md)，不复制**。本节只补本报告深挖出的**机制性**限制（来源均为官方）：

- **值解析不缓存是全局取舍**：高频访问同一组合值必须客户端自建缓存（`UsdAttributeQuery`/`UsdResolveInfo` 是官方提供的 opt-in 设施，[G1]）——把 USD 嵌进高频回路（如评测闭环）时，这是第一个要设计的东西。
- **动画值强度序优先于时间序**：跨源动画合并不可能，Value Clips 是唯一官方出路（[T1][G1]）——若做导出适配器，逐 tick 状态流应写成 timeSamples 单源，不要指望多层拼接。
- **编辑串行化**：写层期间该 Stage 的所有读被禁止（无锁读的前提），高频写 + 并发读的负载形态与 USD 核心相抵（[G1] Change Processing）。
- **组合成本结构**：场景打开时间随层文件数与引用结构增长，秒~分钟级；payload 分层 + 模型层级视图是官方缓解方案（Model Hierarchy 亚秒级可用，[G3]）；"What makes a USD scene heavy/expensive?" 官方清单包括 crate 优先、层计数、（大型文本 usda 的）解析与内存（[G3]）。
- **Instancing 的覆盖税**：instance 子树内不可覆盖（[G1]）；Inherits 常驻订阅成本（[G1]）——资产结构设计直接决定组合成本。
- **Flatten 不可并行**：烘焙组合"is generally memory and compute-intensive, and will not, at this time, benefit from multithreading"（[G1] Flatten 词条）。
- **内存分配器敏感性**：官方指南实测 jemalloc 相对 glibc 在 stage 打开与 Hydra 成像上"by a factor of 2x on a 16 core Intel workstation"（[G3]）——性能测量环境声明需包含 allocator。
- 官方性能度量页面的告诫口径（机器规格可变等）互链事实卡 §1，不复制。

## 4. 与 OmniWorld 的关系深化（World Contract 视角）

对照 [00-总体设计.md §2](../../design/00-总体设计.md)（World Contract 权威文本）逐元拆解：

- **identity**：OpenUSD 的身份是 `SdfPath` 层级命名空间，且是**组合的产物**——reference 重命名目标 prim（"In the composed namespace, the prim name Marble is gone"，[G1] References）、relocates 再映射（[G1]）；同一逻辑对象在不同上下文中路径不同，"No GUIDs" 是官方权衡后的决定（互链事实卡 §2.1）。OmniWorld：runtime 唯一铸造单调 id、永不复用，参与者只能描述特征——两者**不可调和**：USD 里"同一个东西"靠上下文判断，OmniWorld 里靠铸造裁决。导出适配器（阶段 C 后）若做 World Contract → USD，只能做**快照式映射**（每 tick 把 id → 当前 stage 路径物化），不能指望共享身份语义（推断，依据：上述官方命名空间可变机制 + 官方无 GUID 声明）。
- **time**：TimeCode 无单位 double 坐标 + timeSamples + 逐弧 Layer Offset（乘法可组合的时间重映射，[G1]）——时间是**采样坐标系**，可以有任意偏移/缩放视角，无因果性承诺。OmniWorld：单一 tick 单调时钟域，墙钟仅诊断（契约③）。导出映射是纯重标记（tick → TimeCode，`timeCodesPerSecond` 定标）（推断，依据：[G1] TimeCode 词条 + [G2] 时间采样数据模型）。
- **ownership**：OpenUSD 的"作者"单位是**层**（edit target 决定 opinion 落点，"You can think of Edit Targets as an extension of the idea of 'selecting a layer' in Photoshop"，[G1] EditTarget 词条），多作者合法、由 LIVERPS 隐式仲裁、无账本。OmniWorld：每字段**单一作者**、非拥有者结构上无写接口、全部主张走 Proposal 五元组进信念账本（契约④⑤⑥）。这组对立最有迁移价值的是两个概念：**Edit Target**（"往哪写"是一等 API 概念——OmniWorld 的 Proposal 路由可对照其形态）与 **session layer**（应用状态与资产数据的结构性分离、不随数据保存，[G1] Session Layer——对应 OmniWorld "诊断/会话状态不入真值账本"的既有纪律）。
- **confidence**：无对应物。最接近的机制是 variant selection（在离散备选中做确定性选择，[G1]）与 specializes 的"兜底意见"（§2.3），但都不携带概率语义、不参与校准。OmniWorld 强制单标量 [0,1] 只喂 ECE（契约⑦）——导出时置信度无处可放，只能丢弃或编码为自定义 metadata（后者会脱离 Core Spec 词汇域，需 owner 决策；此为开放问题，见 §5）。
- **可吸收的工程纪律**（非契约项）：① defer-dirty 通知纪律（[G1] Change Processing 官方建议）与 OmniWorld tick 日志的"逐阶段延迟"计量目标同向；② 依赖注册表驱动的精确失效（[C1]）是"最小重算"的成熟范式，OmniWorld 的 per-tick 全量推进若出现性能压力，这是第一个可借鉴的失效模型；③ prim index 可诊断性（usdview Composition tab、`DumpToDotGraph`、TF_DEBUG `PCP_PRIM_INDEX`，[S1]）——"组合过程可打印成图"值得 OmniWorld 的 Proposal→裁决链对齐。
