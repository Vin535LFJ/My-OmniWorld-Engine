## 0. 摘要

**它是什么**：Isaac Sim 是 NVIDIA 建在 Omniverse Kit 之上的机器人仿真平台（官方 README 原话："a simulation platform built on NVIDIA Omniverse"，https://github.com/isaac-sim/IsaacSim，检索 2026-11-05）。它本身不是传统意义的"引擎单体"，而是一个 **Kit 应用 = 一份声明式扩展依赖清单**（`source/apps/isaacsim.exp.base.kit`，tag v6.0.1）：渲染、物理、传感器、合成数据、ROS 2 全部以 Kit 扩展形态挂进同一个 OpenUSD 场景。

**核心原理一句话**：一张 OpenUSD 场景经组合求值后被 Fabric 拉平成 GPU 友好的平铺运行时，四类子系统（RTX 渲染传感器、PhysX/Newton 物理、Replicator 标注、OmniGraph/脚本）读写同一份场景状态——**传感器即渲染器**（相机、Lidar、Radar 都在渲染时用 RTX 硬件光线追踪产生），**物理可插拔**（PhysX 与 Newton 经 app 文件级开关互换）。

**最关键的三个机制**：① **Kit/Fabric 双层场景**——USD 管"资产与组合语义"（文件、Layer、LIVERPS），Fabric 管"活状态"（post-composition 平铺、按属性名相邻存储、CPU/GPU 同步、仿真↔渲染 ringbuffer）；② **RTX Sensor SDK 传感器管线**——渲染时 GPU 光线追踪 + GenericModelOutput (GMO) AOV，材质光谱一致（透明/反射表面、无线电波段反射率）；③ **PhysX 5 TGS 求解器 + GPU pipeline，且引擎可整组替换**——6.0.1 的 `isaacsim.exp.full.newton.kit` 直接以 `enabled = false` 关闭全部 `omni.physx.*` 扩展、换装 Newton + Warp。

**对本项目的意义**：Isaac Sim 永远不会进 OmniWorld 产品路径（事实卡 §6"⑤ 明确让渡"），但它的三个机制层是本仓库的现成对照系：Fabric 的"组合态 vs 运行态分离 + 仿真/渲染不同速率 ringbuffer"正是 World Contract ③时间域要回答的问题；Replicator 的"传感器 → annotator → COCO/KITTI writer"与本仓库 D 系列"真实帧 + 标注入环"同构；Isaac Lab 的"Kit-less Newton 默认安装"是"轻物理内核 + 重渲染可选"架构的一手实例。

## 1. 项目定位与生态位

与事实卡 [../projects/isaac-sim.md](../projects/isaac-sim.md) §6 互链：map 索引行 = **Simulation adapter**（Study: sensor/simulation integration；Do not copy: Full simulator）。生态位上 Isaac Sim 是 NVIDIA 机器人栈的**中间层**——向下是 Omniverse Kit/RTX/PhysX 基础设施，向上是 Isaac Lab（RL/IL 框架）、Isaac ROS（机器人栈验证）与 Replicator SDG 工作流（官方参考架构五任务组，[参考架构页](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/introduction/reference_architecture.html)，检索 2026-11-05）。官方首页把这条链说成一句话："Import robots and scenes from URDF, MJCF, Onshape CAD, or USD. Simulate with PhysX or Newton, add RTX and physics-based sensors, generate synthetic data, prepare robots for Isaac Lab, and validate robot stacks with ROS 2."（[6.0.1 首页](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/index.html)，检索 2026-11-05）。

## 2. 原理详解

### 2.1 架构总览：Kit 应用 + 五个机制层

**怎么做的**：Isaac Sim 6.0.1 的本体在仓库里的形态是"若干 `.kit` 应用文件 + 一大批 `isaacsim.*` 扩展"：

- `source/apps/` 下并列多个应用 flavor：`isaacsim.exp.full.kit`（主应用）、`isaacsim.exp.full.fabric.kit`（Fabric 场景委托 flavor）、`isaacsim.exp.full.newton.kit`（Newton 物理 flavor）、`isaacsim.exp.full.streaming.kit`（WebRTC 流送 flavor）等 13 个（GitHub API `repos/isaac-sim/IsaacSim/contents/source/apps?ref=v6.0.1`，检索 2026-11-05）。
- `.kit` 文件是纯声明：`isaacsim.exp.base.kit`（`version = "6.0.1"`）的 `[dependencies]` 段逐行列出扩展名——`isaacsim.core.experimental.*`、`isaacsim.sensors.experimental.rtx`、`isaacsim.replicator.writers`、`omni.physx.tensors`、`omni.replicator.core`、`omni.replicator.replicator_yaml`、`omni.syntheticdata`、`semantics.schema.*` 等（源码原文，https://github.com/isaac-sim/IsaacSim/blob/v6.0.1/source/apps/isaacsim.exp.base.kit，检索 2026-11-05）。**应用 = 扩展依赖图的入口节点**，这就是 Kit 的组合模型。
- Kit 层的定义（官方 Kit 手册）：Kit 是 "the SDK for building your own Omniverse applications"，"brings together" USD/Hydra、Omniverse Client Library、Carbonite、RTX Renderer、Scripting、omni.ui；扩展是 "versioned packages with a runtime enabled/disabled state. These extensions can depend on other extensions"；Carbonite 提供 "core functionality of all Omniverse apps"，其插件是 "shared libraries with C-style interfaces, which can be dynamically loaded and unloaded"（[Kit 手册 kit_overview](https://docs.omniverse.nvidia.com/kit/docs/kit-manual/latest/guide/kit_overview.html)，检索 2026-11-05）。
- 官方参考架构页把这套东西组织成五个任务组：Geometry Authoring（SimReady 资产）→ Importing Assets（URDF/MJCF/Onshape/CAD 导入器）→ Scene Setup（PhysX 物理 + RTX/物理传感器 + MDL 材质）→ Interaction with the Digital Twin（GUI / Standalone Python / Extensions / OmniGraph 四通道）→ Use Cases（Isaac Lab、SDG、ROS 2、CI/CD）（[参考架构页](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/introduction/reference_architecture.html)，检索 2026-11-05）。

**数据流总图**（各小节逐一展开）：

```
USD 文件/Layer（资产、组合语义、文件存储）
        │  组合求值（pre-composition）
        ▼
   OpenUSD Stage ── 组合结果拉平 ──▶ Fabric 运行时（post-composition 平铺、GPU 同步）
        │                                   │
        │              ┌────────────────────┼──────────────────────┐
        ▼              ▼                    ▼                      ▼
  RTX 渲染器      PhysX / Newton        Replicator             OmniGraph / 脚本
  (相机帧+RTX传感器)  (USD schema→物理→    (render product →      (事件图/Python 编排)
                    写回 USD/Fabric)     annotator → writer)        │
        └────────────┴──── 写回 Fabric/USD ▲│─────────────────────┘
                                            │(外部数字孪生交互)
                                    ROS 2 / WebRTC / tensor API
```

官方对这个"共享运行时"的一句话概括："USD scene, physics state, sensors, semantics, and graphs in one runtime"（[6.0.1 首页](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/index.html)，检索 2026-11-05）。

**为什么这样设计**：机器人仿真的负载异质性极端——照片级渲染、大规模物理、传感器建模、数据集生成、ROS 通信是五套完全不同的技术栈。Kit 的扩展组合让每套栈独立演进（扩展有独立版本、可启停），`.kit` 文件把"这个发行版包含什么"变成可 diff 的声明；USD 作为唯一场景表示让"资产导入 → 场景编辑 → 仿真 → 合成数据 → 部署"全程一个数据模型（官方四徽章之一 "USD-native — One scene representation from asset import to deployment"，[6.0.1 首页](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/index.html)，检索 2026-11-05）。

**代价是什么**：① 组合性换启动成本——官方 README 明说首次加载 "may take up to several minutes as Extensions and Shader are loaded and cached. The subsequent startup time should be in the ranges of 10-30 seconds"（v6.0.1 README:158，检索 2026-11-05）；② 构建期必须联网拉 Omniverse Kit SDK 与扩展——v6.0.1 README 原话（逐行核对）："**Internet Access**: Required for downloading the Omniverse Kit SDK, extensions, and tools."；扩展注册表指向 NVIDIA blob——v6.0.1 的 `isaacsim.exp.full.newton.kit:110` 与 `isaacsim.exp.full.fabric.kit:46` 均在 `[settings.exts."omni.kit.registry.nucleus".registries]` 下含 `{ name = "isaacsim/prod/6.0", url = "https://ovextensionsprod.blob.core.windows.net/exts/isaacsim/prod/6.0/shared" }`——这正是事实卡 §2.2"重应用形态"结论的机制根源；③ 场景状态在 USD/Fabric 双轨之间存在一致性窗口（§2.2）。

### 2.2 Kit/OpenUSD 场景层：USD（组合语义）与 Fabric（活运行时）的双层结构

**怎么做的**：Isaac Sim 的场景语言就是 USD——"The language used in Isaac Sim to describe the robot and its environment is the Universal Scene Description (USD)"，选择理由是交换、Layer/Variants 协作、"working on assets without overwriting and erasing someone else's work"（[6.0.1 OpenUSD Fundamentals](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/omniverse_usd/open_usd.html)，检索 2026-11-05）。所有资产必须先转 OpenUSD，默认单位米（[参考架构页](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/introduction/reference_architecture.html)，检索 2026-11-05）。USD 数据模型本身的细节（Layer/组合弧/LIVERPS/Opinion）在 [OpenUSD 项目卡](../projects/openusd.md) §1，此处不重复。

关键的机制增量在 **Fabric**：USD 的组合求值贵且存储以"prim 为中心"，而渲染/物理/OmniGraph 每帧需要的是"以属性为中心"的高频平铺访问。NVIDIA 在 Kit 里加了一个独立运行时：

- Fabric 是 "the Omniverse library that enables high-performance creation, modification, and access of scene data"，负责 "communication of scene data between CPU and GPU and other Fabric clients on a network"；数据 "can be populated from the local composed USD stage, but may also be generated procedurally or populated over the network"（[USD, Fabric, and USDRT](https://docs.omniverse.nvidia.com/kit/docs/usdrt.scenegraph/latest/usd_fabric_usdrt.html)，检索 2026-11-05；以下 Fabric 引文同源，关键句已用 curl 逐字复核）。
- 存储布局："Internally, Fabric stores data so that all properties of the same name and type are stored adjacent to each-other in memory"，官方称之为 "fast, GPU-friendly, and straightforward to parallelize at scale"——即按属性名组织的 SoA（structure of arrays）布局。
- 查询效率："Fabric indexes data and provides a query API to allow systems such as physics and rendering to get only the data they need, without having to traverse the scene each frame"；"Prim discovery with Fabric is very fast (O(1)) because Fabric's internal storage organizes prims by shared sets of properties"。
- **速率解耦**："Fabric also provides a ringbuffer between simulation and one or more renderers to allow them to run at different rates." ——仿真与渲染以不同频率跑，中间用 ringbuffer 隔开。
- GPU 同步："Fabric manages synchronization of data to and from the GPU for GPU-accelerated operations and rendering."
- 两者的官方对照表：Fabric 数据视图 = "Post-composition only"（USD = "Pre- and post-composition"）；持久性 = "Transient, in-memory only"（USD = "File-based storage"）。
- 上层 API 是 USDRT："mirrors the USD API (and is pin-compatible in most cases), but reads and writes data to and from Fabric"——为开发者提供从 USD 到 Fabric 的低迁移成本通道。

源码级证据：主应用 flavor `isaacsim.exp.full.fabric.kit`（`execFile = "isaac-sim.fabric"`）显式依赖 `usdrt.scenegraph` 与 `omni.physx.fabric`，并设置 `omnihydra.useFastSceneDelegate = true`、`app.vulkan = true`（https://github.com/isaac-sim/IsaacSim/blob/v6.0.1/source/apps/isaacsim.exp.full.fabric.kit，检索 2026-11-05）——即渲染遍历走 Fabric 支撑的 fast scene delegate 而非逐次回查 USD。

**为什么这样设计**：这是"资产语义"与"活状态"的分工——USD 管"世界是什么样（含组合规则）"，Fabric 管"世界此刻的值"。物理侧的映射规则由 omni.physx 定义："The USD stage is parsed and physics objects are created within PhysX."，步进后 "Simulation output is written to USD after each step."（[Omni Physics Simulation Control](https://docs.omniverse.nvidia.com/kit/docs/omni_physics/latest/dev_guide/simulation_control/simulation_control.html)，检索 2026-11-05）。甚至多 tick 仿真时间也以 Fabric prim 传达：6.0 changelog 明言 "Multitick simulation time is now communicated via the `/ExternalSimulationTime` Fabric prim"（[6.0.1 release notes](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/overview/release_notes.html)，检索 2026-11-05）。

**代价是什么**：① 一致性窗口——"Post-composition only" 意味着 Fabric 看不到组合规则，USD 才是权威；双轨之间需要显式同步，官方手册承认两端数据视图与持久性不同（同上 usdrt 页对照表）；② Fabric 是 Omniverse 侧实现而非 OpenUSD 标准的一部分——写进 Fabric 的代码绑定 NVIDIA 运行时（OpenUSD 卡 §2.2 已裁定 USD Fabric 数值主张未证实，本报告只引官方定性描述）；③ 对"想要单层真相"的系统（如本引擎）来说，这种双层结构是把复杂度从"求值"转移到"同步"。

### 2.3 RTX 渲染管线与传感器仿真：传感器即渲染器

**怎么做的**：Isaac Sim 的传感器分两族，官方参考架构页明确二分：RTX 渲染传感器（相机/Lidar/Radar）与物理型传感器（contact、IMU、force、effort、proximity）（[参考架构页](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/introduction/reference_architecture.html)，检索 2026-11-05）。

**渲染器本体**：Omniverse RTX 渲染器是 "a scalable photo-real renderer leading the convergence of real-time and offline rendering"，两种模式都 "solving the rendering equation with a path tracing-based algorithm"：RTX Real-Time 2.0 = "a physically based path-tracing rendering mode leveraging the NVIDIA DLSS suite of neural rendering technologies"；RTX Interactive (Path Tracing) = "designed to accurately simulate the behavior of light"（[RTX Renderer 文档](https://docs.omniverse.nvidia.com/materials-and-rendering/latest/rtx-renderer.html)，检索 2026-11-05）。材质用 NVIDIA MDL（物理基材质着色语言，参考架构页）。

**相机**："Isaac Sim cameras are USD Camera prims rendered by the RTX renderer."；运行时 `CameraSensor` 包装 `RtxCamera`（套 `OmniSensorAPI` schema），"creates a Replicator render product at a specified resolution, attaches annotators (rgb, distance_to_camera, semantic_segmentation, etc.), and provides get_data()"，返回 `(warp.array, info_dict)`；`tick_rate` 控制渲染频率（0 = 每仿真帧渲染），`TiledCameraSensor` 把多相机打进一个 tiled render product，官方称对 RL 多环境工作流 "significantly more efficient than one render product per camera"（[6.0.1 Camera 传感器页](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/sensors/isaacsim_sensors_camera.html)，检索 2026-11-05）。

**Lidar/Radar/Acoustic**：机制与相机同源但走专用 AOV——"RTX Lidar sensors are simulated at render time on the GPU with RTX hardware. Their results are then copied to the GenericModelOutput AOV for use."，场景侧用 "OmniLidar prims, with the OmniSensorGenericLidarCoreAPI schema applied"（[6.0.1 RTX Lidar 页](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/sensors/isaacsim_sensors_rtx_lidar.html)，检索 2026-11-05）。统一抽象是 "RTX sensors in Isaac Sim use the Omniverse RTX Renderer's RTX Sensor SDK to sense the environment"，从而 "enabling interaction with materials in visual and non-visual spectra"——官方给的例子："an RTX-based Lidar can model returns from light interaction with transparent or reflective surfaces, and an RTX-based Radar can model returns accounting for material emissivity and reflectivity in the radio spectrum"（[6.0.1 RTX Sensors 页](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/sensors/isaacsim_sensors_rtx.html)，检索 2026-11-05）。辅助数据通道由 prim 属性控制："The amount of auxiliary data carried in each GMO frame is controlled by the `_replicator:rendervar:GenericModelOutput:channels` attribute on the sensor prim."（同上）。渲染变量层面，Replicator 的 render product 支持自定义 render variables "['GenericModelOutput', 'RtxSensorCpu', 'RtxSensorGpu', 'RtxSensorMetadata']"（[omni.replicator.core API](https://docs.omniverse.nvidia.com/kit/docs/omni_replicator/1.12.16/source/extensions/omni.replicator.core/docs/API.html)，检索 2026-11-05）。

**传感器节拍**：6.0 的 multitick rendering 把传感器调度挂到物理时间——"Cameras and RTX Lidars can be scheduled and rendered at rates and offsets driven by physics simulation time."（[6.0.1 release notes](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/overview/release_notes.html)，检索 2026-11-05）。

**为什么这样设计**：把所有"光学/电磁回波类"传感器统一到渲染管线，换来的是**材质一致性**——同一个场景材质既决定 RGB 像素也决定 Lidar 回波/Radar 反射，不需要为每种传感器维护单独的几何查询路径；path tracing（而非光栅化）则保证深度/分割等几何真值与成像物理同源。这也是官方合成数据主张的基础（§2.5）。

**代价是什么**：① **RT Cores 硬门槛**——官方 requirements 明说 "GPUs without RT Cores (A100, H100) are not supported."（事实卡 §4，链接不复制）；② **DLSS 噪声代价**——"Without DLSS Ray Reconstruction support, images appear significantly noisy when using the RTX Real-Time render mode"（RTX Renderer 文档）——DLSS 是神经网络重建，对"像素即数据"的传感器仿真而言，降噪器本身成为保真度变量；③ **多 GPU 传感器稳定性**——官方警告 "On systems with multiple GPUs (MGPU), some RTX Lidar assets can sometimes cause a fatal application crash"（RTX Lidar 页）；④ 传感器保真度分级官方只给"渲染时 RTX 光线追踪"的定性描述，RTX Sensor SDK 的独立文档与逐参数回波模型 **UNVERIFIED**（§5）。

### 2.4 PhysX 5 求解角色与可插拔物理后端

**怎么做的（物理如何进入场景）**：物理属性全部以 schema 表达——"The physics properties of assets are all well-defined using USD Physics Schemas and Physx Schemas."（[6.0.1 Simulation Fundamentals](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/physics/simulation_fundamentals.html)，检索 2026-11-05）。物理后端是 "powered by the NVIDIA PhysX SDK"，覆盖 "Rigid Body Simulation, Character Control, Deformable Body Simulation, Particle Simulation, and Articulations"，碰撞近似支持 "convex hull, convex decomposition, bounding sphere, bounding box, and SDF collision meshes"（[参考架构页](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/introduction/reference_architecture.html)，检索 2026-11-05）。omni.physx 的职责边界："The USD stage is parsed and physics objects are created within PhysX."；如需则执行 "PhysX cooking and convex decomposition"；步进后结果 "written to USD after each step"（[Omni Physics Simulation Control](https://docs.omniverse.nvidia.com/kit/docs/omni_physics/latest/dev_guide/simulation_control/simulation_control.html)，检索 2026-11-05）。机器人关节走 articulation："An articulation is an optimized simulation structure for jointed bodies that provides superior performance, fidelity"（Simulation Fundamentals）；且 "joint-related quantities like link incoming joint forces or joint drive targets have a one-to-one correspondence in the PhysX SDK and USD"——USD 与 PhysX 概念一一对应，这正是"场景描述与求解器解耦"的数据基础。

**求解器（TGS vs PGS）**：PhysX 5 提供两种迭代约束求解器，官方 5.4.1 文档逐字（curl 复核）："PhysX supports two types of solvers: the Projected Gauss-Seidel-style (PGS) solver and the Temporal Gauss-Seidel (TGS) solver, which was introduced in PhysX 5.1."；"TGS is generally the recommended solver and will become the default soon"；两者 "utilize the same equations of motion and feature implicit time discretization with approximations"。TGS 的本质是**子步化**："the TGS substepping scheme is conceptually similar to calling the PGS solver with a smaller timestep multiple times, each time only requesting a single solver iteration."——位置迭代数即子步数，换来 "Improved convergence / Improved handling of high-mass ratios / Improved joint drive accuracy"，代价是 "Each TGS iteration is generally a little slower than PGS."。默认迭代配置："The solver iteration count defaults to 4 position iterations and 1 velocity iteration."（[PhysX 5.4.1 RigidBodyDynamics](https://nvidia-omniverse.github.io/PhysX/physx/5.4.1/docs/RigidBodyDynamics.html)，检索 2026-11-05）。Omni Physics 侧的约束："Two different solver strategies are available: PGS (Projected Gauss-Seidel) and TGS (Temporal Gauss-Seidel)."；"PGS converges more slowly but is less prone to overshooting compared to TGS."；且 "its not possible to change PhysxScene solver type in runtime"（Omni Physics Simulation Control，检索 2026-11-05）。

**GPU pipeline**："Enabling GPU rigid body dynamics turns on GPU-accelerated contact generation, shape/body management and the GPU-accelerated constraint solver."；"Turning on GPU broad phase replaces the CPU broad phase with a GPU-accelerated broad phase."——两个组件可独立开关；实现 "in CUDA and requires SM6.0 (Pascal) or later"；无兼容设备时 "simulation will fall back onto the CPU"（[PhysX 5.4.1 GPURigidBodies](https://nvidia-omniverse.github.io/PhysX/physx/5.4.1/docs/GPURigidBodies.html)，检索 2026-11-05）。

**物理引擎可插拔（PhysX ↔ Newton）**：这是 6.0 系列最有信息量的源码级机制——`isaacsim.exp.full.newton.kit`（v6.0.1，`execFile = "isaac-sim.newton"`）不写一行物理代码，只做扩展拓扑手术：依赖 `"isaacsim.physics.newton" = {}`、`"isaacsim.physics.newton.tensors" = {}` 与 `"omni.warp.core" = {}`（Newton 是 Warp 内核），同时把 PhysX 全家禁用——`"omni.physics.physx" = { enabled = false }`、`"omni.physx.bundle" = { enabled = false }`、`"omni.physx.fabric" = { enabled = false }`、`"isaacsim.sensors.physx" = { enabled = false }`……连 PhysX 系传感器扩展一起关闭（https://github.com/isaac-sim/IsaacSim/blob/v6.0.1/source/apps/isaacsim.exp.full.newton.kit，检索 2026-11-05）。应用层之上的 API 层已经引擎无关："The isaacsim.core.experimental APIs provide an engine-agnostic interface to physics data."；"C++ and Python tensor APIs for Newton are similar to PhysX."；"URDF and MJCF importers apply Newton schemas to imported assets."；"ROS 2 Bridge handles the Newton backend similarly to PhysX."（[6.0.1 release notes](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/overview/release_notes.html)，检索 2026-11-05）。

**为什么这样设计**：① TGS 子步化是用计算换关节保真——机器人仿真里关节误差（joint stretching）直接决定 sim-to-real 质量，官方文档原文点明 TGS 适合 "objects with lots of joints and a small tolerance for joint error"（PhysX 5.4.1 RigidBodyDynamics）；② GPU pipeline 是为大规模并行 RL 服务（同页与 Isaac Gym 论文一脉相承，见 §2.6）；③ 引擎插拔则把"物理后端"从运行时选项提升为**发行形态**（独立 .kit flavor + 独立可执行文件 `isaac-sim.newton`），避免运行时混用两个求解器的不变量灾难。

**代价是什么**：① 求解器类型是**场景级不可变属性**——"This choice is an immutable scene property that must be set before the scene is constructed."（PhysX 5.4.1 RigidBodyDynamics），Omni Physics 侧同样声明运行时不可改（Simulation Control）；② GPU pipeline 有明确降级清单：凸包超过 64 顶点或 64 多边形、或每面超过 32 顶点时接触回落 CPU（原文："Convex hulls with more than 64 vertices or polygons or with more than 32 vertices per-face will have their contacts processed by the CPU rather than the GPU"）、"Any pairs requesting contact modification will be processed on the CPU"、"joint projection, CCD and triggers are not GPU accelerated"、"Scene queries are executed on the CPU"；GPU 缓冲不能动态增长——"the GPU simulation is not able to dynamically grow all buffers"，默认值 "generally sufficient for scenes simulating approximately 10'000 rigid bodies"，超限时 "the system will issue warnings and discard overflowing objects like contacts/constraints/pairs"（GPURigidBodies）——**静默丢对象是真实风险**；③ Newton 后端在 6.0 仍标 experimental（事实卡 §2.1，链接不复制）；④ TGS 的官方"introduced in PhysX 5.1"表述与社区常见的"PhysX 4 已有 TGS"记载不一致，本报告以官方文档原文为准，版本史考据不展开（§5）。

### 2.5 Replicator 合成数据管线：render product → annotator → writer

**怎么做的**：Omniverse Replicator 是 Isaac Sim 的 SDG 框架（官方首页："Script randomization, capture sensor outputs, and write labeled datasets"，[6.0.1 首页](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/index.html)，检索 2026-11-05），本体是 Kit 扩展 `omni.replicator.core`（官方 README 自述 "a core extension for [NVIDIA Omniverse]"，https://docs.omniverse.nvidia.com/kit/docs/omni_replicator/latest/source/extensions/omni.replicator.core/docs/index.html，检索 2026-11-05）。管线四段式：

1. **Render Product**：渲染产品是管线的数据源——"A RenderProduct describes images or other file-like artifacts produced by a render, such as rgb (LdrColor), normals, depth, etc."（curl 逐字复核，[omni.replicator.core API](https://docs.omniverse.nvidia.com/kit/docs/omni_replicator/1.12.16/source/extensions/omni.replicator.core/docs/API.html)，检索 2026-11-05）。同分辨率同相机的 render product 会复用。
2. **Annotator**：锚定定义（curl 逐字复核）——"Annotators provide ground truth annotations corresponding to the rendered scene. Within Replicator, there are multiple off-the-shelf annotators"（[ext_replicator annotators_details](https://docs.omniverse.nvidia.com/extensions/latest/ext_replicator/annotators_details.html)，检索 2026-11-05）。即标注不是事后 CV 推理，而是渲染管线同源产出的几何/语义真值。
3. **Writer**：消费标注落盘。Isaac Sim 的 writers 扩展机制："Each writer registers specific annotators required for their data format and handles the processing pipeline from raw render products to formatted output files or tensor streams."；"Writers support both local filesystem and S3 storage backends"（[isaacsim.replicator.writers 扩展文档](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/py/source/extensions/isaacsim.replicator.writers/docs/index.html)，检索 2026-11-05）。
4. **Orchestrator**：驱动循环——`rep.orchestrator.preview()/run()/stop()`（omni.replicator.core README，检索 2026-11-05）；教程中单步推进是 `rep.orchestrator.step(delta_time=0.0, rt_subframes=rt_subframes)` + `rep.orchestrator.wait_until_complete()`（standalone 同步）或对应 `*_async` 变体（script editor）（[6.0.1 Scene-Based SDG 教程](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/replicator_tutorials/tutorial_replicator_scene_based_sdg.html)，检索 2026-11-05；以下引文同源）。

**COCO/KITTI 产出**：官方参考架构页对标注集合的原话："2D bounding boxes, 3D bounding boxes, semantic and instance segmentation masks, normals, depth, pointclouds, and more"，"data being written in common formats like COCO and KITTI formats"（[参考架构页](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/introduction/reference_architecture.html)，检索 2026-11-05）。6.0.1 教程实例化了三套 writer：BasicWriter（annotator 组合含 rgb、bounding_box_2d_tight、semantic_segmentation、distance_to_image_plane、bounding_box_3d、occlusion，DiskBackend 落盘）、KittiWriter（带 `colorize_instance_segmentation` 与 `mapping_dict` 逐类映射）、CocoWriter（带 `coco_categories` schema：names/ids/supercategories/colors/isthing）。随机化与真值生成在同一个循环里：`rep.functional.randomizer.scatter_2d(..., check_for_collisions=True)` 撒料、材质/灯光 randomizer 由 OmniGraph 自定义事件触发（`rep.trigger.on_custom_event`）、甚至 SDG 前先跑一段物理仿真让箱子落下（physics dt = 1/90）等速度收敛——最后 `rep.set_global_seed(42)` 级别可复现（同上教程）。

**为什么这样设计**：真值与渲染**同源**是这套管线的立身之本。官方公告博客（2021-11-09）的定义："an engine for generating synthetic data with ground truth for training AI networks"，目的是 "narrow the appearance and content gaps"；真值侧的优势说得更直白："Synthetic data provides ground truth that humans can't label"（深度/速度/多传感器跟踪），遮挡目标也有真值——"the ground truth is available automatically and accurate at a pixel level"；整条管线 "time accurate and deterministic, the dataset can be created in repeatable way"（[NVIDIA 博客](https://blogs.nvidia.com/blog/drive-sim-replicator-synthetic-data-generation)，检索 2026-11-05）。Writer 与 Annotator 解耦则让"标注格式"成为纯下游选择——COCO/KITTI 只是把合成真值对齐评测生态的适配层。

**代价是什么**：① **渲染是逐帧硬成本**——每帧真值都来自 path tracing 级渲染，吞吐受 GPU 档位约束（16 GB 门槛见事实卡 §4）；② **标注数据的组织成本**——annotator 返回的是 warp.array + info_dict（Camera 传感器页），语义分割的 id→类别映射、instance id 稳定性由场景 semantics schema 决定，构造不当的语义层级会让 writer 产出废数据（教程需显式 mapping_dict/coco_categories 即证据）；③ **写入器归属在 6.0.1 有重组痕迹**——`isaacsim.replicator.writers` 的 API 列表已不含 BasicWriter/CocoWriter/KittiWriter（列出的是 PoseWriter/DOPEWriter/YCBVideoWriter/PytorchWriter 等，且 DOPE/YCB 已标 deprecated），而教程与参考架构仍在用这三个名字——具体扩展归属未定位到 6.0.1 逐字文档，**UNVERIFIED**（§5）；④ 需要手动控制 capture 时机（教程 `rep.orchestrator.set_capture_on_play(False)`），管线不是"开着就自动录"。

### 2.6 与 Isaac Lab 的分层关系：多后端框架与 Kit 应用的解耦

**怎么做的**：Isaac Lab 是 Isaac Sim 之上的 Python 框架，不是 Kit 应用。其包结构（GitHub API `repos/isaac-sim/IsaacLab/contents/source/isaaclab/isaaclab`，检索 2026-11-05）分层清晰：`app`（启动器）/ `sim`（仿真上下文与配置）/ `assets` + `actuators` + `sensors` + `scene`（实体层）/ `managers`（事件、动作、奖励、终止等管理器）/ `envs`（管理器式与直接式环境）/ `renderers` / `terrains` / `controllers` / `cloner`。官方 README 定义："a GPU-accelerated, open-source framework designed to unify and simplify robotics research workflows"，且是 **multi-backend**："It is a multi-backend framework supporting physics and rendering through Newton, OVRTX, OVPhysX, and NVIDIA Isaac Sim."；最关键的一句："Kit-less Newton workflows do not require Isaac Sim."（https://github.com/isaac-sim/IsaacLab，检索 2026-11-05）。

**多后端的机制证据**（源码）：`isaaclab/sim/simulation_cfg.py` 中 `render_interval: int = 1`——官方 docstring "The number of physics simulation steps per rendering step. Default is 1."（物理步与渲染步天然可不同频，默认 1:1）；物理后端是配置对象："Physics manager configuration. Default is None (uses PhysxCfg()). ... a different config (e.g., NewtonManagerCfg) to use a different physics backend."（https://github.com/isaac-sim/IsaacLab/blob/main/source/isaaclab/isaaclab/sim/simulation_cfg.py，检索 2026-11-05）。相机传感器把 render-product 与 annotator 管理委托给 `isaaclab.renderers` 的 `BaseRenderer`——源码 docstring 原句（camera.py:681-683）："This function delegates all render-product and annotator management to the :class:`~isaaclab.renderers.base_renderer.BaseRenderer` created in :meth:`__init__`."；Replicator 在该文件中**不是委托对象**，仅作为 annotator 输出的文档参考出现（camera.py:168 "Summarizing from the `replicator extension`_, the following sensor types are supported:" 与 camera.py:198 的 annotator 输出参考链接）（检索 2026-11-05）。

**与 Isaac Sim 的版本锚定**：IsaacLab README 的兼容矩阵——main 与 release/3.0.0 对 Isaac Sim 6.2，v3.0.0-EA 对 6.1，v2.x 对 4.5–5.1（检索 2026-11-05）；`isaacsim` extra 锚定 6.2.0.0、"Isaac Sim 5.1 and older are unsupported"（事实卡 §1，链接不复制）。

**为什么这样设计**：这是 Isaac Gym 路线的架构延续。Isaac Gym 论文（NVIDIA，2021）的核心主张："Both physics simulation and the neural network policy training reside on GPU"，数据 "by directly passing data from physics buffers to PyTorch tensors without ever going through any CPU bottlenecks"，换来 "2-3 orders of magnitude improvements"（[arXiv:2108.10470](https://arxiv.org/abs/2108.10470)，检索 2026-11-05）。Isaac Lab 论文自述 "the natural successor to Isaac Gym"，架构主张是 "high-fidelity GPU parallel physics, photorealistic rendering, and a modular, composable architecture"，并把 "upcoming integration with the differentiable, GPU-accelerated Newton physics engine" 列为下一步（[arXiv:2511.04831](https://arxiv.org/abs/2511.04831)，检索 2026-11-05）。分层关系因此是：**Kit 应用（Isaac Sim）提供场景/渲染/传感器基础设施，Python 框架（Isaac Lab）在其上（或脱离其）组织 RL/IL 训练循环**；训练吞吐场景（Newton standalone，无渲染）与保真传感器场景（Isaac Sim + RTX）可以分叉选型。

**代价是什么**：① 版本耦合仍在——`isaacsim` extra 锚定具体版本（6.2.0.0），Isaac Lab 主线当前不锚定本报告主角 6.0.1（事实卡 §7-2 已标 UNVERIFIED，链接不复制）；② "Kit-less" 只对物理为主的工作流成立——一旦需要 RTX 相机/传感器，就回到 Kit 应用与 16 GB 显存世界；③ multi-backend 的抽象漏隙在源码可见——Newton 的执行器模型是独立配置对象（`use_newton_actuators` docstring 说明 PhysX 与 OVPhysX "execute them through a shared host"，Newton 在 solver 内执行），后端间行为差异要靠框架层抹平。

## 3. 能力边界与工程现实

官方承认的机制性限制（硬件/OS/许可层全部链接事实卡 §2/§4，不复制）：

| 机制层限制 | 官方原文/出处 |
|---|---|
| 求解器类型运行时不可变 | "This choice is an immutable scene property that must be set before the scene is constructed."（PhysX 5.4.1 RigidBodyDynamics，检索 2026-11-05） |
| GPU pipeline 静默降级/丢弃 | 凸包超 64 顶点/多边形或每面超 32 顶点→接触回落 CPU；contact modification 回落 CPU；"joint projection, CCD and triggers are not GPU accelerated"；超限 "discard overflowing objects like contacts/constraints/pairs"（GPURigidBodies，检索 2026-11-05） |
| GPU buffer 固定容量 | "the GPU simulation is not able to dynamically grow all buffers"（同上） |
| TGS 迭代更贵 | "Each TGS iteration is generally a little slower than PGS."（RigidBodyDynamics） |
| DLSS 降噪是保真变量 | "Without DLSS Ray Reconstruction support, images appear significantly noisy when using the RTX Real-Time render mode"（RTX Renderer 文档，检索 2026-11-05） |
| MGPU 传感器崩溃风险 | "On systems with multiple GPUs (MGPU), some RTX Lidar assets can sometimes cause a fatal application crash"（RTX Lidar 页） |
| 启动/构建成本 | 首次加载 "up to several minutes"；构建需联网拉 Kit SDK 与扩展 blob（README，检索 2026-11-05） |
| 场景状态双轨 | Fabric "Post-composition only" / "Transient, in-memory only"，与 USD 文件存储需显式同步（usdrt 文档） |
| 破坏性迁移 | 6.0.0 移除 `omni.isaac.*` 兼容 shim（事实卡 §2.1，链接不复制） |

**与本仓库红线的关系**：事实卡 §2.2 已裁定"重应用形态与参考模式零外部依赖结构性相斥"，其机制根源即本报告 §2.1 的证据——Kit SDK/扩展 blob 联网拉取 + 扩展缓存启动成本。这从原理层（而非仅许可层）排除了进程内嵌入。

## 4. 与 OmniWorld 的关系深化（World Contract 四轴视角）

以 [00-总体设计.md §2](../../design/00-总体设计.md) 的 World Contract 四元组（identity / time / ownership / confidence）为镜：

- **identity**：USD/Fabric 的身份是**命名空间路径**（prim path），层级可组合可重命名；语义身份靠 `semantics.schema.*` 扩展的标签（base.kit 依赖清单含 `semantics.schema.editor`/`semantics.schema.property`）。Isaac Sim 没有"runtime 唯一铸造、单调不复用"的实体 id 概念——实例化克隆（`isaacsim.core.cloner`）后的关联是调用方的事。对照本引擎契约 ②：**关联判定作为可替换组件**正是 USD 生态缺失而评测必需的一环——Replicator 的 instance segmentation 之所以能工作，依赖场景作者预先把 instance id/语义写进 USD，而不是运行时铸造。
- **time**：Isaac Sim 的世界有三层时钟——物理步（"Simulation steps per second are determined in the Physics Scene"，默认 60，Simulation Fundamentals）、渲染帧（`render_interval` 定义每渲染步多少物理步，Isaac Lab 默认 1）、传感器节拍（multitick："Cameras and RTX Lidars can be scheduled and rendered at rates and offsets driven by physics simulation time"，6.0 release notes）。把三者粘起来的是 Fabric："Fabric also provides a ringbuffer between simulation and one or more renderers to allow them to run at different rates."，仿真时间本体甚至是一个 Fabric prim（`/ExternalSimulationTime`）。对照本引擎契约 ③（单一 tick 单调时钟域，墙钟仅诊断）：Isaac Sim 的答案相反——**承认多速率域，用 ringbuffer/属性传达而非统一时钟**。这对 OmniWorld 的启示是双向的：本引擎的单一 tick 域换来字节级可复现（ADR-0009 语义），Isaac Sim 的多速率域换来传感器级真实感；若未来闭环评测要接 Isaac Lab，tick 映射层（物理步 → 引擎 tick）是必须显式声明的边界。
- **ownership**：USD 场景是**多 opinion 无主**结构（OpenUSD 卡 §2.2"无活世界所有权语义"），Fabric 数据同样无作者模型——"Data in Fabric can be populated from the local composed USD stage, but may also be generated procedurally or populated over the network"，谁都能写。Isaac Sim 靠**扩展职责边界**隐性划权：物理结果由 omni.physx 独家写回（"Simulation output is written to USD after each step."），渲染真值由 Replicator 独家产出——但这是约定不是结构。对照本引擎契约 ④（每字段单一作者、非拥有者结构上无写接口）：**闭环路线已裁定"仿真器作为外部真值权威，引擎镜像进 WorldState"**（[2026-10-27 交互闭环笔记](../2026-10-27-interactive-closed-loop-route.md) §2 方案 (b)）——Isaac Sim 的"物理独占写回"模式恰好是该方案在对方侧的镜像：对接面上两边都满足"单一作者"，引擎侧 WorldState 的所有权裁决不必因接入而妥协。
- **confidence**：Replicator 的真值是**构造即真值**（渲染同源、像素级、无误差通道——博客："the ground truth is available automatically and accurate at a pixel level"），没有 per-detection 置信度语义；传感器噪声只存在于物理建模层（材质光谱交互），不进入标注数据结构。对照本引擎契约 ⑦（强制单标量 [0,1] 自报置信度、零裁决权力、只喂校准）：合成数据管道里的"完美真值"与真实观测流的"带噪观测"是两个评分空间——这正是本仓库 D4 `ScoreSpace::ObservationUV` 裁定"结论只对同一观察序列内有效"的镜像问题：**把合成真值直接当真实观测基准用，会隐式把校准指标的整体口径换成另一个空间**。若未来用 Replicator 产数据入 D 系列面板，标注侧需显式声明"构造真值"性质，与 D2/D3 的真实标注区分。

**对 D 系列数据管道的对照结论**：Replicator 的"传感器 → annotator → COCO/KITTI writer"链与本仓库 `node tools/coco_to_panel.mjs` 的"数据集标注 → 面板真值"链**同构但方向相反**——Replicator 从场景生成标注，D 系列从既有标注构造场景。Isaac Sim 证明"标注格式对齐评测生态"是仿真器侧的成熟做法；它没有回答的（也是 OmniWorld 的差异化空间）：标注进环后的**关联判定、置信度语义、逐 tick 账本**——World Contract ②⑤⑦ 恰好是它的空白区。
