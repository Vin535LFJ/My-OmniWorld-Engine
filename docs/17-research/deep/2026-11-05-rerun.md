## 0. 摘要（给赶时间的人）

Rerun 是面向物理 AI（机器人/空间智能）的多模态时序数据基础设施：一个用 Rust 写的记录/存储/查询/可视化/训练数据层。**核心原理一句话：把所有模态（图像、点云、变换、标量、视频、音频）的数据统一降维成「entity path（身份轴）× timeline（时间轴）双轴索引下的 Apache Arrow 列式 chunk」，让记录、网络传输、落盘、内存存储、查询、渲染、训练全链路共享同一物理数据形状，中间零格式转换。**

最关键的三个机制：

1. **Chunk 贯穿一切**：chunk（Arrow RecordBatch + `rerun:`/`sorbet:` 语义元数据）是 SDK 微批的产物、datastore 的存储单元、.rrd 的消息载荷、查询引擎的扫描单位、直通 GPU 的渲染数据源——同一结构走完全程（[R7][R8][R9]）。0.18 重写后标量场景写/摄入提速 100x、内存降 35x（[R10]）。
2. **双轴模型 + partial updates**：数据按 (entity path, timeline, component batch) 稀疏落库，latest-at/range 两类查询让"15–60 Hz 的图像与 500–1000 Hz 的 IMU"不必对齐即可共存，对齐是查询期（fill_latest_at / AsOf-Join 式 latest-at）而非入库期的事（[R11][R12][R13]）。
3. **framing 稳定 / 模型版本化的 .rrd 落盘**：线性追加的 framed 消息流（protobuf 外壳 + Arrow IPC 载荷）+ 可选 footer 实现廉价随机访问；压缩按消息粒度、只在省 ≥10% 字节时启用；文件格式承诺 framing 不变，而数据模型（Sorbet schema）版本化、加载时内存迁移（[R9]）。

对本项目的意义：Rerun 的 entity path × timeline 双轴与 World Contract 的 identity / time 轴**同构可比**，其"后写胜出 + 历史全留"的冲突语义与契约⑥"v1 只记录不仲裁"是同一设计选择在不同层的表达（§4）；同时其 150–174 MB SDK、GPU/Wgpu 渲染依赖、非字节级回归的二进制工件，从反面印证了本仓库"零外部依赖 + JSON 工件字节级回归"的自研静态查看器路线（互链事实卡 §6，不重述）。

## 2. 原理详解（本报告核心）

> 阅读指引：每节按「怎么做（机制）→ 为什么这样设计（取舍）→ 代价是什么（限制）」三层展开；节末列支撑来源（[Rn] 见 §6）。Rerun 是开源项目，"官方文档"与"官方源码"可互相印证——凡源码级陈述均给出 crate/文件路径。

### 2.1 架构总览：一个 Arrow 贯穿到底的五段流水线

**怎么做。** 官方架构文档（ARCHITECTURE.md）给出的数据流是：

```
SDK (Python/Rust/C++) → Arrow 编码 → .rrd 文件 或 gRPC → Viewer/Server
  → 内存 store (re_chunk_store) → 查询层 (re_query / re_dataframe / re_datafusion)
  → views（每个渲染帧由 viewer 查询 store 并喂给渲染器）
```

- **Logging SDK**："The logging SDK:s encodes the data using Apache Arrow"，产物可以"transmitted over gRPC to either a Rerun Viewer or a Rerun Server"，也可以存为 .rrd（[R3]）。
- **Viewer** 自带完整服务端能力："The viewer includes a Chunk Store (in-memory database for logged data) and a gRPC endpoint that accepts streamed data from the SDK"——viewer 不只是渲染器，它自己就是 ingestion 终点（[R5]）。
- **Catalog server**（`rerun server`）提供数据组织与索引：Dataset（相关录制集合）→ Segment（注册进 dataset 的单个 .rrd），本地版把 rrd 文件**原地索引**（元数据在内存），协议是 redap（Rerun Data Protocol）；Hub 是同 API 的托管版，差别只在"连接已有服务器 vs 自己起一个"（[R5]）。
- **查询与训练**：Catalog SDK 返回 Apache DataFusion dataframe；训练侧 "a dataloader runs a query against the catalog and yields training batches"（[R4][R5]）。
- **crate 分层纪律**（源码层）：仓库按文件夹分层——`crates/store`（re_chunk / re_chunk_store / re_chunk_index / re_chunk_optimizer / re_log_types / re_log_encoding / re_log_msg / re_sorbet / re_protos / re_types_core / re_sdk_types 等，经 GitHub API 实测列出，2026-11-05）、`crates/store_app`（re_query / re_dataframe / re_datafusion / re_entity_db / re_server）、`crates/views`（re_view_spatial / re_view_time_series / re_view_tensor / re_view_graph / re_view_map / re_view_audio）、`crates/top`（re_sdk / rerun_py / rerun_c / re_viewer / rerun-cli）、渲染层 re_renderer（wgpu）。官方规则："Every arrow points downwards, because the folders are layers: a crate may only depend on its own folder or one below it"，由 CI 脚本 `scripts/check_crate_dependencies.py` 强制（[R3]）。

**为什么这样设计。** 取舍核心是**单一物理表示的多路复用**：Apache Arrow 同时充当网络传输、.rrd 落盘与内存 store 的编码（"Apache Arrow is used for network transport, `.rrd` storage, and the in-RAM store"，[R3]）。同一列式形状意味着：SDK 编码一次，传输不重编码，落盘不重编码，viewer 拿到的就是磁盘上那份字节形状，甚至"a chunk's columns can pass untouched through the store to a visualizer, copied straight to the GPU"（[R10]）。这把传统 robotics 栈里"记录器→转换器→数据库→可视化器"每层一次序列化转换的税砍到零，也是它能宣称 log/query/visualize/train 共用一层数据层的结构前提。

**代价。**
- 全链路绑定 Arrow：用户自定义数据必须能映射进 `rerun:*` 元数据约定的 Arrow 列（§2.2/§2.3），非表状数据要靠 Blob/Tensor 组件包装。
- web viewer 是 32-bit Wasm，"limited to ~2 GiB memory in practice"且"runs single-threaded, making it generally slower than native"（[R5]）——同一架构在浏览器里打了折扣。
- viewer 进程同时承担 store + gRPC 服务 + 渲染，内存上限行为见 §3（RAM 满 75% 默认丢最老数据）。

**来源**：[R3] ARCHITECTURE.md（2026-11-05）；[R4] what-is-rerun（2026-11-05）；[R5] how-does-rerun-work（2026-11-05）；[R10] column-chunks 博客（2026-11-05）；GitHub API crate 列表实测（2026-11-05）。

### 2.2 双轴数据模型：entity path（身份）× timeline（时间）× component batch（值）

**怎么做。** Rerun 的数据模型是一个"time-aware Entity Component System"（[R11]）：实体（entity）用组件批（component batches）随时间变化来表达（"you model your data using entities (roughly objects) with batches of components that change over time"，[R12]）。三个正交轴：

- **身份轴 = entity path**。"all entities within Rerun have a unique entity path"；`/` 分隔的层级路径，"each entity is a folder, and a component is a file"；同一路径可挂多个 archetype，组件以 archetype 为命名空间（`Points3D:positions` vs `Mesh3D:vertex_positions`）互不冲突；`__` 前缀保留给 SDK（`__properties`、`__warnings`）（[R6]）。反复向同一路径 log 即更新该实体。
- **时间轴 = timeline**。"Each piece of logged data is associated with one or more timelines."内建两条：`log_time`（temporal，默认开）、`log_tick`（sequence，默认关）；用户经 `rr.set_time("frame_idx", sequence=…)` 增加任意多条。三种索引类型**全部编码为 i64**：sequence（逻辑序号）、timestamp（Unix epoch 纳秒）、duration（纳秒时长）（[R7]）。一次 log 调用同时落在所有激活的 timeline 上（`set_time` 之后的数据"add the logged points to the timelines frame_idx and sensor_time, **as well as** the automatic log_time timeline"）。
- **值轴 = component batch**。"the value of a given component at a given point in time is always itself a list — or a batch — of values."批内单个值叫 instance；批**不可变**——"When data is logged to a component for a given time point, the corresponding batch is immutable... The entire batch must be logged again, and this will replace the previous one."而"the previously logged batches will remain in storage"（[R15]）。
- **身份的物理层 = RowId/TUID**：每行数据有一个 128-bit TUID——"Time-ordered globally unique 128-bit identifier"，上半 64 bit ≈ 自 epoch 的纳秒，下半是"Initialized to something random on each thread, then incremented for each new Tuid"；big-endian 编码使"the raw bytes of the Tuid sorts in time order"（crates/utils/re_tuid/src/lib.rs 模块文档，[R16]）。
- **static data**：`static=True` 的数据"belongs to all timelines (existing ones, and ones not yet created) and shadows any temporal data of the same type on the same entity"——用于场景级不变量（坐标系、AnnotationContext、街道网格），典型用法如 `rr.log("/", rr.ViewCoordinates.RIGHT_HAND_Z_UP, static=True)`（[R7][R19]）。

**为什么这样设计。**
- **path 做"人类语义身份"、TUID 做"物理唯一身份"是两层分离**：entity path 面向组织与导航（层级、transform 传播、blueprint contents 匹配），RowId/TUID 面向存储排序与全局唯一（跨进程无协调的单调序，`Tuid::new_after(min)` 处理时钟超前的异机器铸造）。这让"名字可重组、物理序不乱"同时成立。
- **i64 统一编码**让三种语义的索引进同一条存储/索引/查询管道——时间轴在物理层不区分"逻辑帧号"和"墙钟纳秒"，只有解释差异。
- **batch 不可变 + 历史全留**是 append-only 事件溯源语义：同 (path, component, time) 重复 log 只改变"谁在查询时胜出"（后写者），不破坏已入库数据——这是部分更新（§2.7）与可回放性的地基。
- **static shadow**解决"配置类数据不该有时间轴又要覆盖一切"的问题：为场景设置（scene-setting）数据免掉逐帧重发的成本，且语义上"先于"任何时序数据。

**代价。**
- **身份正确性靠用户自律**：path 是用户起的字符串名，Rerun 不验证"两次 log 到同一 path 的是不是同一个东西"——关联判定完全外置给用户；这与 World Contract ②（runtime 唯一铸造、参与者不能自带 id）是对照面（§4）。
- **join 是 per-archetype 约定而非全局规则**：组件间按"第 n 个 instance 对应第 n 个"组合（"clamping semantics, which can also be seen as a left-join using the primary component"），但 Mesh3D 的 `vertex_colors` join `vertex_positions` 而 `triangle_indices` 不 join（[R15]）——不规则关系要靠文档逐个声明。
- **static shadow 是无条件全局覆盖**："unconditionally shadows any temporal data"（[R7]），没有部分覆盖或优先级仲裁——一旦 static 数据存在，同实体的时序数据在该组件上失效，回放"历史"时也被 shadow。
- **同一 path 的旧批次永久留存**：替换语义是查询期的，存储上是 append-only——高频重写同一点会产生存储放大（官方未给清理原语，只有 `rr.Clear` tombstone 语义，见 [R6] 相关 howto 索引）。

**来源**：[R6] entity-path（2026-11-05）；[R7] timelines（2026-11-05）；[R12] latest-at（2026-11-05）；[R15] component batches（2026-11-05）；[R16] re_tuid 源码（2026-11-05）。

### 2.3 Chunk——贯穿始终的唯一数据单元（微批 → compaction → 查询 → GPU）

**怎么做。** 官方定义："A Chunk is the core datastructure at the heart of Rerun: it dictates how data gets logged, injected, stored, and queried"；物理形态是 "an Arrow-encoded, column-oriented table of binary data"，列结构为：**1 个控制列（RowId）+ 每 timeline 一个 index 列 + 每组件一个数据列**，数据列内部是 List 数组——"Each row of the list array corresponds to a single time point"，利用变长列表实现"component batches to have different lengths at each time point"（[R8][R15]）。chunk 的生成与合并走两级：

1. **SDK 侧 micro-batching**：行式 `rr.log` 产生一行 → "That row is then passed to a batcher, which appends the values from the row to the current chunk for the entity path"——**按 entity path 分桶累积**；后台线程按"时间与空间阈值，先到先触发"刷出：默认 `RERUN_FLUSH_TICK_SECS=0.2`（200 ms；使用网络 sink 时 8 ms）、`RERUN_FLUSH_NUM_BYTES=2097152`（2 MiB）、`RERUN_FLUSH_NUM_ROWS=u64::MAX`（等效不限行）（[R8][R17]）。
2. **store 侧 compaction**："The Rerun datastore continuously compacts data as it comes in, in order find a sweet spot between ingestion speed, query performance and memory overhead"；阈值 `RERUN_CHUNK_MAX_BYTES=393216`（384 KiB）、`RERUN_CHUNK_MAX_ROWS=4096`，且对未按时间排序的 chunk 用更严的 `RERUN_CHUNK_MAX_ROWS_IF_UNSORTED=1024`（[R18]）。

关键性质（0.18 重写的收益，[R10]）：索引指向 chunk 列而非单行，"chunks are usually sorted so they tend to be fast to search"；"Large enough chunks can be inserted untouched to the store and the index can be built from the header alone"；"Latest-at queries are cached by the viewer, keeping the performance impact of larger chunks negligible"；基准：9 plots × 5 series × 50k f64 = 2.25M 标量，"an improvement of 100x for write and ingestion speed, and 35x for memory overhead"。

**为什么这样设计。**
- **旧架构的失败模式是行索引**："The old data store kept an index of individual rows, which would dominate both ingestion time and memory usage for recordings with large amounts of small rows"——Rerun 原来按"大块少点"（点云/张量，<100k 时间点）调优，标量时间序列是灾难（[R10]）。chunk 化后最坏情况从"每标量一行索引"变成"每 chunk 一条索引"。
- **目标尺寸区间**让"低频大块（点云/图像）+ 高频小信号（标量/IMU）"的混合录制在磁盘上块尺寸均匀——官方原话：列式设计"allows for keeping chunks within a target size range, even for recordings that combine low frequency but large data ... with high frequency but small signals (tall columns)"（[R8]）。
- **两级批处理同构**：SDK 微批"trades off a small amount of latency and memory use in favor of more efficient transfer and ingestion"；store compaction "is very similar to, and has many parallels with, the micro-batching mechanism running on the SDK side"（[R8][R17][R18]）——同一阈值思想在两端各跑一次，网络两端都以 chunk 为单位。
- **列式让 compaction 变成纯 Arrow 操作**：小块按列拼接即可，无需理解组件语义；"Compaction guarantees chunks aren't too small, simplifying range-query caching——only unsorted chunks need a sorted cache copy"（[R10]）。

**代价。**
- **行式 API 的固有延迟**：微批为吞吐牺牲少量延迟/内存（官方明示）；对延迟敏感的 live 场景要把 flush tick 压到 8 ms（网络 sink 默认）或自配 [R17]。
- **阈值是全局环境变量**，不能按实体/组件分级（`RERUN_CHUNK_MAX_*` 均为进程级默认）[R18]。
- **unsorted chunk 查询更贵**：乱序写入触发 1024 行的更低 compaction 上限，等于强制更碎的 chunk（[R18]）——乱序摄入是性能悬崖。
- chunk 数量过多仍需人工干预：官方提供专门的 "Optimize chunk count" howto 与 `rerun rrd compact` CLI（[R10][R18]）——离线重整是常规运维动作，不是自动收敛。

**来源**：[R8] chunks（2026-11-05）；[R10] column-chunks 博客（2026-11-05）；[R15] component batches（2026-11-05）；[R17] micro-batching（2026-11-05）；[R18] store compaction（2026-11-05）。

### 2.4 Arrow 列式落盘（.rrd）：framing 稳定、数据模型版本化的设计取舍

**怎么做。** .rrd（与 .rbl 同格式，"purely a filename hint"）是"a linear sequence of framed messages"加可选 footer（[R9]）：

| 结构 | 内容 |
|---|---|
| StreamHeader（12 B，LE） | FourCC `RRF2`（4B）+ 版本（4B）+ compression（0=Off/1=LZ4）+ serializer（2=Protobuf；1 曾为 MsgPack，现拒绝）+ 2B 保留 |
| 消息流 | 每条消息 16 B 头（kind: u64 + payload_len: u64）+ protobuf 外壳载荷；四种 kind：`End(0)`（含可选 footer）、`SetStoreInfo(1)`（声明 store，须先于其数据，后到者胜）、`ArrowMsg(2)`（"carries the actual data"——一条 Arrow IPC 载荷 = 一个 chunk，"the bulk of every RRD"）、`BlueprintActivationCommand(3)`（blueprint 原子激活，"the Viewer never sees a half-loaded blueprint"） |
| 压缩 | 仅 ArrowMsg 载荷可压，**按消息独立**（同一文件可混压/不压）；LZ4 "only where it saves at least 10% of the bytes"——视频样本等不可压数据保持裸 Arrow IPC |
| Footer（可选） | 一个 Arrow RecordBatch 清单，**每 chunk 一行**：chunk id、字节偏移、压缩/未压缩大小、每组件与每 timeline 的统计、`schema_sha_256`；读取方式：EOF−12 处读 `RRF2`+`FOOT`+num_entries，再向前 num_entries×20 B 读 StreamFooterEntry（start u64 + len u64 + crc32 u32）；CRC = xxh32(payload)，固定种子 7850921（"RERUN" 的 base-26）；有 footer 时读者"pull only the chunks it actually needs ... without reading any chunk it does not care about" |

**为什么这样设计。**
- **追加写 = 记录流的天然形态**：录制是 append-only 事件流，线性消息序列让 SDK 流式写出、文件可 cat/merge（`rerun rrd merge` 合并多文件并折叠 trailer）。
- **footer 换随机访问**：没有 footer 时"triggers a linear scan, which is semantically equivalent—just slower for partial reads"；有 footer 时 catalog server 能以小内存做随机拉取——这是"磁盘上的 chunk 索引"，与 2.3 的内存索引同构。
- **framing 与 schema 分层版本化**："The framing described in File layout is considered stable and we have no plans to change it"，而数据模型（Sorbet——"how chunks, archetypes, components, and timelines map onto Arrow column names, types, and metadata"）"is versioned and subject to change"，加载时 in-memory 自动迁移；任何 CLI 重写 rrd 的往返"都是一次迁移"（[R9]）。源码层印证：re_sorbet crate "Handles the structure of arrow record batches and their meta data for different use cases"，定义 `SorbetBatch`（"An arrow record batch that follows a specific schema"）与更严格的 `ChunkBatch`（"Every ChunkBatch can be converted into a SorbetBatch, but the opposite does not hold"），并提供 `migrate_record_batch` / `migrated_schema_from_ipc` 迁移入口（crates/store/re_sorbet/src/lib.rs，[R16]）。
- **对既有格式的取舍判断**（0.32 博客，[R14]）：Parquet"row groups 不重叠、缺 schema evolution"不适配多速率流；MCAP 是"opaque-message container"，扫描慢；Lance 行对齐、多速率流 null 膨胀；NVIDIA NCore "closed, non-Arrow schema"。Rerun 选择自研 container + 裸 Arrow，换来 lakehouse 式元数据层：异构 chunk schema 可在查询时即时合并，加新字段（如 IMU 新通道）无需重写历史数据。

**代价。**
- **版本兼容是硬边界**：`RRF0`/`RRF1` "recognized but rejected with OldRrdVersion"；"Legacy RRDs whose Version field is older than 0.23 are currently rejected"，迁移必须经旧版 Rerun；SDK `save` 模式只保证相邻 minor 版本兼容（[R9]；事实卡 §2.1 已核，互链不复述）。
- **framing 承诺只覆盖 framing**：Sorbet 层"may change"——跨大版本的程序化读写要跟进 schema 迁移，不是一次性冻结。
- **footer 是可选项**：非正常关闭或历史文件无 footer → 线性扫描；多文件拼接产生多 trailer，需 merge 收敛。
- **对 OmniWorld 的直接影响**：.rrd 是二进制 Arrow 容器，进不了 `benchmarks/regression/` 的字节级回归证据链（事实卡 §6 已判定，互链不复述）。
- xxh32 是非加密校验（防损坏，不防篡改）——对"证据链"用途需要外层哈希。

**来源**：[R9] rrd-format（2026-11-05）；[R14] data-layer-for-robot-learning 博客（2026-11-05）；[R16] re_sorbet 源码（2026-11-05）。

### 2.5 传输与部署分层：gRPC 三服务、逻辑录制合并与 catalog（dataset/segment/layer）

**怎么做。** 所有组件间通信走 gRPC，proto 在 `crates/store/re_protos/proto`，全部服务器开 gRPC reflection（[R20]）：

| 服务器 | 默认地址 | 服务 |
|---|---|---|
| Viewer（`rerun`） | 127.0.0.1:9876 | `MessageProxyService`、`ViewerControlService`、`RerunCloudService` |
| SDK proxy（`rerun --serve-grpc`） | 127.0.0.1:9876 | `MessageProxyService` |
| Catalog server（`rerun server`） | 127.0.0.1:51234 | `RerunCloudService` |

`MessageProxyService` "carries logged data between SDKs and Viewers"；`ViewerControlService` "drives a running Viewer, and is what the MCP server uses"；`RerunCloudService` 是 catalog + 查询 API——viewer 内嵌一个只收本机连接的 internal catalog（当前加载的录制），`rerun server` 则面向任意客户端服务其启动时注册的 rrd 文件与表（[R20]）。

- **多机/多进程汇聚**："Multiple processes or machines can produce separate .rrd files that share the same recording ID and application ID"——viewer 按 (application_id, recording_id) 池化合并为**逻辑录制**；"from the perspective of the Viewer, recordings are never 'completed'"——永远可续流（[R21]）。共享 application_id 的录制共享同一 blueprint。
- **catalog 数据模型**：Dataset → Segment（"Its recording ID becomes the segment ID, and its application ID is discarded"）；segment 可含多层（layer），"each backed by a .rrd file"，多个物理录制叠成一个逻辑 segment（[R21]）。
- **SDK 侧出口**：5 种 operating modes（spawn / connect_grpc / serve_grpc / save / stdout）+ `set_sinks` 并发多路（写盘同时推 viewer）（[R22]，细节互链事实卡 §5）。
- **Hub 的扩缩方式**：开源 server 在内存里维护 catalog 元数据、原地索引磁盘 rrd；Hub 提供托管持久存储并"mediates direct selective-streaming from object storage so CPU/GPU jobs fan out near the data, minimizing egress costs"——存储/计算分离（[R5][R14]）。

**为什么这样设计。**
- **viewer = 服务器**：把 ingestion 端点内嵌 viewer，单人单机场景零部署（`rr.spawn` 一个进程全搞定）；同一套 proto 又让"本地文件、本地 server、云端 Hub"是同一 API 的三种后端——"The APIs are the same either way; Hub changes what runs underneath, not what you do"（事实卡 §3 已引）。
- **逻辑录制按 ID 池化而非按文件**：分布式采集（多机多进程）不需要中心协调器，各写各的 rrd，汇聚是读取期的纯函数——与 RowId 的"跨进程无协调唯一"（§2.2）配套。
- **blueprint 走同一数据通道**：blueprint 也是 recording（"Blueprints are also recordings, albeit ones containing layout information instead of data"，[R21]），`BlueprintActivationCommand` 保证原子激活——**viewer 的配置本身是流数据**，可版本控制、可程序化生成、可远程更新（§2.7）。

**代价。**
- **本地 catalog 元数据在内存**："the local open-source server indexes RRD files on disk and keeps catalog metadata in memory"（[R5]）——大规模注册是 Hub（商业层）的场景。
- **gRPC 面无稳定性承诺**：服务命名仍是 `rerun.cloud.v1alpha1.*`（[R20]；事实卡 §2.1 已核）。
- **viewer internal catalog 只收本机连接**——跨机访问 viewer 内的数据要经 proxy/forward，官方未给方案（未核验，见 §5）。

**来源**：[R5] how-does-rerun-work（2026-11-05）；[R14] data-layer 博客（2026-11-05）；[R20] gRPC API（2026-11-05）；[R21] recordings（2026-11-05）；[R22] operating-modes（事实卡已核，2026-11-05）。

### 2.6 查询引擎：latest-at / range 双查询 + dataframe 查询（AsOf-Join 语义）

**怎么做。** "All data that gets sent to the Rerun viewer is stored in an in-memory database, and there are two core types of queries"（[R12]）：

- **latest-at**："Latest-at queries collect the latest version of each of an entity's components at a particular time."这允许"draw the current state of an object that was updated incrementally"——例如只重发 mesh 顶点，材质与三角索引沿用旧值。0.19 博客给出工程口径：viewer 的时间滑杆"does a latest-at query at 60fps"，语义上"resembles an AsOf Join in other systems"（[R11]）。
- **range**："Range queries instead collect all components associated with times on a time range."驱动"any visualization where data from more than one time is shown at the same time"——时序曲线、多帧点云叠加（[R12]）。
- **dataframe 查询**（数据出）：面向 ML 的行对齐视图——选定 index（timeline）后"a row is produced for each distinct index value for which there is at least one value in the filtered content"，组件列永远是 List（空 List = 被清除）；`fill_latest_at=True` 做"latest-at/forward fill semantics"，且"There is no staleness limit"（不限回看深度）；`index=None` 则每 segment 一行、只取 static 数据；结果是无执行即不计算的 DataFusion lazy dataframe（[R13]）。无服务器路径：`ChunkStore.reader()` 对本地 rrd 直接跑同一查询（[R13]）。
- **chunk processing API**（0.32+，管道式数据进/出/变换）：Readers（`RrdReader`/`McapReader`/`DatasetEntry.segment_store()`）→ LazyChunkStream → transform → sink；`LazyStore` 是索引驱动按需加载，"Filters applied to a LazyStore stream ... are pushed down to the chunk index, so only matching chunks are loaded"；`ChunkStore` 则全量物化（内存随录制规模涨）。配套 Lenses（声明式 reshape 语言，灵感 jq）[R23]。

**为什么这样设计。**
- **把时间对齐放进数据库层**：传感器天然多速率（"perception data ... 15-60Hz" vs "motion IMU data (500-1000Hz)"），表格化后极稀疏，传统管线各自手写对齐、易错；Rerun 的立场是"robotics-style primitives"必须内建——"It's not enough to attach some semantics to specific robotics messages, all your data systems should maintain and use those semantics"（[R11]）。latest-at 就是内建的 AsOf join。
- **partial updates 靠"查询语义 × chunk 存储"共同支撑**："the query semantics that power the Rerun Viewer, coupled with our chunk-based storage, make it possible to log only the components that have changed"（[R12]）——没重发的组件自动沿用最近值，这正是高吞吐下图像/点云/标量能共存一条时间线的关键（§2.7）。
- **latest-at 可缓存**：chunk 按时间有序（compaction 保证）使最新值查询退化为"每个 chunk 的尾部扫描"，viewer 缓存后 60 fps 可行（[R10]）。
- **dataframe 查询与 viewer 查询共享同一套语义**（fill_latest_at = latest-at 的批形态），保证"看到的就是查到的"（[R12][R13]）。

**代价。**
- **latest-at 不插值**：官方自认"Time-alignment can get a lot more complex that latest-at queries though, e.g. if you need to do motion interpolation"（[R11]）——需要插值的场景（连续控制、姿态平滑）要自己出数据库。
- **fill_latest_at 无 staleness 上限**：时间过滤只筛行、不限制回填用的值（[R13]）——对训练数据质量是隐性风险（陈旧值可无声填入），需要用户自建护栏。
- **latest-at 不跨 segment**："Each segment is queried independently"（[R13]）——跨录制对齐不是该 API 的职责。
- range 查询的可视化窗口需用户配置（fixed-window plots 等 howto），默认全量 range 在长录制上有内存代价（未实测，见 §5）。

**来源**：[R10] column-chunks 博客（2026-11-05）；[R11] dataframe 博客（2026-11-05）；[R12] latest-at（2026-11-05）；[R13] dataframe-queries（2026-11-05）；[R23] chunk-processing-api（2026-11-05）。

### 2.7 多模态统一进一条时间线：partial updates + join/splat + transform 图 + blueprint

**怎么做。** "多模态统一"在 Rerun 里不是"统一采样率"，而是五层机制的组合：

1. **一次 log 落多 timeline**：`rr.set_time("frame_idx", sequence=…)` + `rr.set_time("sensor_time", timestamp=…)` 之后的一条数据同时挂在自定义轴与内建 log_time 轴上（[R7]）——多速率数据的"同一事件"在多个时间参照系里同时可寻址。
2. **组件级 partial updates**：archetype 的各组件独立记录，只更新变化的部分（"Update only the colors and radii, leaving everything else as-is"），latest-at 自动补齐未更新组件（[R12]）——15 Hz 图像与 1 kHz IMU 入库时各自稀疏，互不等待。
3. **instance join/splat 跨时刻组合**：主组件（如 Points3D 的 Position3D）决定实例数，次组件少给则"the last instance is repeated as required"（clamping，等价于以主组件为左表的 left-join）；且"joined components do not need to be logged at the same time"——不同时刻分别 log 的组件在查询时组合（[R15]）。
4. **transform 图统一空间**：`Transform3D` 沿 entity path 层级传播（"transforms propagate down the entity tree"）；底层实现是统一的有名帧系统——每个实体路径自动关联一个 `tf#` 前缀隐式帧（如 `/world/robot` → `tf#/world/robot`），未指定帧时按父路径默认（与 ROS tf2 同构的 `parent_frame`/`child_frame` 命名帧是显式替代，优点包括"topology may change over time"）；`Pinhole` 不是普通 archetype 而是"spatial relationships that define projections from 3D spaces to 2D subspaces"——3D→2D 投影与 3D→3D 变换同属一个解析系统，"3D in 2D: 3D objects can be projected through pinhole camera into the view"；`InstancePoses3D` 提供不向子树传播的实例级位姿（instancing）（[R19]）。
5. **blueprint 统一视图状态**：blueprint 是数据——"structured using the same Entity Component System as your recordings, but with blueprint-specific archetypes and a separate blueprint timeline"；viewer 是确定性函数："Takes the active blueprint and active recording, then queries view archetypes, fetches recording data, renders, and queues any user interactions as new blueprint events on the blueprint timeline"——"Viewer output is a deterministic function of the blueprint and the recording, with minimal persisted state between frames"（[R24]）。viewer 用 egui/eframe immediate-mode GUI："each frame the entire GUI is being laid out from scratch"，渲染层 re_renderer 基于 wgpu（"abstracts Vulkan, Metal, D3D12, D3D11, OpenGLES, WebGL and WebGPU"），native 与 web 同一套代码（[R3]）。

**为什么这样设计。**
- **多模态统一的正确抽象是"共享身份 + 共享查询语义 + 共享空间解析"，不是共享采样**：入库存稀疏（sparse is fine），对齐延迟到查询/渲染时刻按需完成。这把"每帧同步所有传感器"的伪命题换成了"每个消费者在自己需要的时间点做 latest-at"。
- **空间关系放进数据模型而非 viewer 后处理**：Pinhole 与 Transform3D 同构让"2D in 3D / 3D in 2D"是同一套帧解析的副产品（nuScenes/arkit 官方示例均靠此实现）——多模态的空间对齐（图像↔点云↔相机位姿）由数据声明，而非消费代码各写各的投影。
- **blueprint-as-data** 让视图可版本控制、可程序化生成（`rr.send_blueprint()`，可按数据条件生成布局）、可被 SDK 完全操纵而不依赖 viewer 进程；时间轴化的用户交互事件"strengthens future features like snapshots and undo/redo"——**查看器状态也进时间线**，是双轴模型的彻底自应用。

**代价。**
- 空间对齐正确性依赖用户声明正确的 transform 层级；混用命名帧与隐式 `tf#` 帧官方"generally do not recommend"（[R19]）。
- immediate-mode 的成本由官方自认：未来计划包括"caching queries and work submitted to the renderer"与后台线程处理大数据集（[R3]）——当前每帧全量重建 + 同步查询是已知瓶颈面（同 §3）。
- 视频/音频/地理等模态各有专门组件与 view（VideoStream、AssetAudio、GeoPoints…），非通用 chunk 语义一揽子覆盖（[R4] archetype 清单）。
- 自定义可视化（extend-ui）仅 Rust（事实卡 §2.1 已核，互链）。

**来源**：[R3] ARCHITECTURE.md；[R7] timelines；[R12] latest-at；[R15] component batches；[R19] transforms；[R24] blueprints（均 2026-11-05）。

## 3. 能力边界与工程现实（官方承认的机制性限制）

以下只列事实卡 §2 装不下的、本轮新核验的机制性限制；许可/显存/平台边界互链事实卡 §2/§3/§4，不重述。

1. **内存模型是硬上限 + 淘汰制**：官方 howto 原话——"The Rerun Viewer can not yet view more data than fits in RAM. ... When it reaches a certain limit, the oldest data will be dropped. The default limit is to use up to 75% of the total system RAM."（`--memory-limit` / `rr.spawn(memory_limit=…)` 可调）（[R25]）。结合 0.32 博客对 stable rrd 的"old data will always load"承诺：**加载无上限、查看有上限**——超 RAM 录制能被 catalog 查询（按 chunk 选择性拉取），但整体回放进不了单个 viewer。
2. **web viewer 的结构限制**：32-bit Wasm ~2 GiB 实际内存上限 + 单线程，"generally slower than native"（[R5]）。
3. **rrd 兼容边界**（事实卡 §2.1 已核，机制成因见 §2.4）：framing 稳定但 Sorbet 可变；<0.23 拒读；save 只保证相邻 minor 兼容（[R9]）。
4. **查询语义边界**：latest-at 无插值、fill_latest_at 无 staleness limit、不跨 segment（§2.6，[R11][R13]）。
5. **乱序摄入惩罚**：unsorted chunk 触发 1024 行 compaction 上限（§2.3，[R18]）。
6. **UI 架构的已知债务**：immediate-mode 每帧全量重建；官方 future plans 承认要加查询/渲染缓存与后台线程（[R3]）。
7. **扩展边界**：自定义可视化 Rust only（事实卡 §2.1）；catalog gRPC `v1alpha1` 无稳定性承诺（[R20]）。
8. **渲染环境依赖**：Wgpu 后端（vulkan/metal/gl；web WebGPU→WebGL 回退）、Linux/WSL2 驱动成本——互链事实卡 §4，不重述。

## 4. 与 OmniWorld 的关系深化（World Contract：identity / time / ownership / confidence）

> 权威文本：`docs/design/00-总体设计.md` §2（契约速览 + 逐条语义）。本节按四轴逐一对读；对照自研查看器路线（`docs/design/ui-viewer/查看器设计.md`）收尾。

**identity（契约②：runtime 唯一铸造、关联判定可替换）↔ entity path + RowId/TUID。**
Rerun 把"身份"拆成两层：**语义层**是用户命名的 entity path（层级、可读、可重组、可挂 transform 与 blueprint），**物理层**是 128-bit TUID（纳秒时间序 + 每线程随机种子递增，跨进程无协调唯一、字节序即时间序，[R16]）。与我们对照：契约②要求 runtime 是唯一铸造者（单调 id、永不复用）、参与者不能自带 id——Rerun 的 TUID 恰好示范了"铸造层不可伪造、单调不复用"怎么做；但它的**语义层身份（path）完全外置给用户命名**，"怎么算同一个"（关联判定）没有任何 runtime 裁决。这印证了我们把"关联判定"设计为**可替换组件**而非固定规则的必要性：Rerun 的场景（开发者自己组织自己的数据）不需要它，我们的场景（多参与者对账）必须裁决它。另一个可借的机制：`Tuid::new_after(min)` 解决"异机器时钟超前后仍保证排序"——若闭环路线出现多机采集，这是现成的分布式单调 id 设计。

**time（契约③：单一 tick 单调时钟域，墙钟仅诊断）↔ 多 timeline 并存 + i64 统一编码。**
Rerun 允许任意多条 timeline 同时存在且一次 log 多轴落地（[R7]），把"多速率"表达为多参照系并存、查询期对齐（latest-at / fill_latest_at）。我们选择相反的极简：单一 tick 时钟域承载一切因果，墙钟降级为诊断。**两者的共同点是都把墙钟逐出因果层**——Rerun 的内建因果序其实由 RowId/TUID（mint 顺序）保证而非 log_time 墙钟；`log_tick`（sequence）存在但默认关闭，说明官方默认值面向真实传感器流（墙钟不可避免），而我们面向仿真可以纯逻辑时钟。这不是优劣而是场景差：若做闭环路线的录播导出，值得给每个 Proposal 同时打 `tick`（sequence 轴）与可选 `wallclock`（诊断轴）两条 Rerun timeline——它的数据模型原生支持这种"因果轴 + 诊断轴"分离，与契约③同构。

**ownership（契约④⑤⑥：单一作者 / Proposal 写路径 / v1 只记录不仲裁）↔ 后写胜出 + 历史全留。**
Rerun 对同一 (entity, component, time) 的重复 log："the last logged batch will be used, but the previously logged batches will remain in storage"（[R15]）——**冲突不仲裁、历史不覆盖、裁决延迟到查询/展示层**。这与契约⑥"v1 只记录、不仲裁，信念全部留痕、各评各的分"是同一哲学在不同层的实例；连"永不反向覆盖"都对得上（Rerun 旧批次永在存储，我们 belief 永不回写真值）。**关键差异**：Rerun 没有 per-write 的"作者"字段——作者身份隐含在 application_id/recording_id（进程级）里，同进程内两次冲突写入无法区分来源；我们的 Proposal 五元组（producer/tick_observed/target/fields/confidence）把作者作为数据本身。**推论（adapter 设计要点，若闭环路线做 Rerun 导出）**：ownership 必须编码进 entity path 约定（如 `/truth/...`、`/agent/<name>/...`），让"谁写的"成为身份轴的一部分——这正好利用 path 层级语义，但也意味着 Rerun 侧的 ownership 是**约定**而非**契约**。

**confidence（契约⑦：一等单标量 [0,1]、自报正确概率、零裁决权、只喂校准）↔ 数据模型无置信度概念。**
基于 2026-11-05 检索的官方 components 参考索引（~85 个组件，[R4]），不存在通用的 confidence/probability 组件；置信度语义须用户以自定义组件或属性承载。这不是 Rerun 的缺陷（它面向记录而非评测），但说明**置信度作为一等契约成员在我们的数据模型里是结构性的、不是 Rerun 这类通用记录层白送的能力**——belief 层（信念账本）必须自己实现，导出到 Rerun 时 confidence 会退化成一个普通标量组件。

**static shadow（§2.2）↔ 契约⑤"真值永不回写"的边界。**
Rerun 的 static data"unconditionally shadows any temporal data"（[R7]）适合承载世界不变量（地图、坐标系、AnnotationContext——类比我们的真值世界初始条件与场景布局），但它是**覆盖语义**而非**账本语义**：static 一旦写入就遮蔽历史时序数据，回放旧段也生效。若把 belief 导出为 static 会破坏"信念随 tick 变化、逐 tick 评分"的语义——导出 adapter 必须把 belief 全部走时序轴、只把场景级不变量走 static。这一点与 ui-viewer 设计里"指标是累计值快照"的处理互相印证：快照型数据可以 static，账本型数据必须 temporal。

**对自研查看器路线（买 vs 造）的印证。**
正面可借的三条设计判词：(1) "Viewer output is a deterministic function of the blueprint and the recording, with minimal persisted state between frames"（[R24]）——**视图 = 纯函数(数据, 配置)** 与我们"工件内嵌 + 浏览器直开回放"的静态 HTML 路线精神一致；(2) 多 timeline + static shadow + partial updates 验证了"身份+时间双轴"在多模态高吞吐下成立，且不需要实时同步采样；(3) framing 稳定/模型版本化的分层版本策略是二进制工件可持续演化的可抄答案。反面印证（为何不买）：GPU/Wgpu 渲染依赖、150–174 MB SDK、二进制 rrd 进不了字节级回归、web 版本严格匹配——全部与 ADR-0012 零依赖参考模式相反（事实卡 §6 已判定，互链不复述）。触发条件沿用事实卡 §7：闭环路线落地且出现图像/点云级回放真实需求时，先 spike timeline 工件 → `rr.log` 导出 adapter。
